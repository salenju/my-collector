# 01 · 架构总览

## 1. 目标与非目标

### 1.1 目标

| 编号 | 目标 | 验收方式 |
| --- | --- | --- |
| G1 | 在浏览器里 3 秒内记录一条链接或碎片笔记 | 打开即用，粘贴 URL 即自动带出标题 |
| G2 | 打标签、检索方便 | 关键词 + 标签筛选，结果即时呈现 |
| G3 | 多端（PC / 移动）可查看与记录 | PWA 安装到手机主屏；两端看到同一份数据 |
| G4 | 多设备同步、离线可用 | 断网可记录，恢复网络后自动推送 |
| G5 | 数据完全自持，无自建服务、无数据库 | 全部数据是私有 Git 仓库里的 JSON 文件 |
| G6 | 单人自用，不对外开放 | 无注册、无多租户、无分享功能 |

### 1.2 非目标（明确不做）

- 不做用户系统、登录注册、多租户、协作分享。
- 不自建服务端、不引入云数据库（Supabase / Firebase / 飞书均不采用）。
- 不做全文检索引擎（不建倒排索引、不引 Elasticsearch/Meilisearch）。
- 不做社交、公开主页、RSS 输出。
- 不做数据加密存储（Token 与数据都以浏览器／GitHub 自身的安全边界为准，见 08 文档）。

### 2.1 架构核心不变式

1. **数据的唯一真源（Source of Truth）是 GitHub 私有仓库里的 JSON 文件**；IndexedDB 只是缓存 + 待同步队列。
2. **任何一次本地写入都先落地本地、立即返回成功**，网络同步永远是异步的、可失败的、可重试的。
3. **任何一次远端写入都是一次 commit**，写多文件时用 Git Data API 保证原子性（D11）。
4. **前端产物是纯静态文件**，不含任何密钥；PAT 只存在用户设备的本地存储里。
5. GitHub API 是唯一网络依赖（元信息抓取除外），失败时应用必须完整可用（只降级、不白屏）。

## 4. 代码仓库结构

采用 **pnpm workspace 轻量 monorepo**，核心目的是让 Web 与 Chrome 扩展共用同一套数据层与同步逻辑，
避免「网页能同步、扩展不能」这类双实现漂移。

```

│   └── release-extension.yml          # 打包扩展 zip → 挂到 Release
```

## 5. 端到端数据流

### 5.1 冷启动（读路径）

```
打开应用
  └─ 1. 读 IndexedDB 全量快照 ────────► 立即渲染（<100ms，用户可直接操作）
  └─ 2. 读 settings 校验 PAT 是否存在 ─► 无 PAT → 跳设置向导
  └─ 3. 后台 pull()：
         ① GET 分支 ref + commit（空仓库返回 null）
         ② GET /git/trees/{branch}?recursive=1 → 1 个请求拿到全仓库文件 sha
            ├─ 与本地 fileCache.sha 比对，无变化 → 读路径结束（不发多余请求）
            └─ 有变化 → 并发拉取变化的 items/YYYY-MM.json（限额并发 6，带 If-None-Match）
                       └─ 逐条校验 → 按分片与「本地 + outbox」做 LWW 合并 → 单事务写回 Dexie → 刷新 UI
  └─ 4. 若 outbox 非空 → 触发 push()
```

### 5.2 记录一条收藏（写路径）

```
用户在 /new 粘贴 URL
  └─ 元信息抓取（可选、可失败）：代理链 → 回填 title / excerpt / favicon
  └─ 用户确认标签 → 点「保存」
  └─ 1. Dexie 事务：写 item + 写 outbox(upsert) + 更新内存快照
  └─ 2. UI 立即反馈成功（乐观更新，"待同步"角标）
  └─ 3. debounce 2s 后 push()：
         ├─ 取 Web Locks('sync') 防止多标签页并发提交
         ├─ 依据 outbox 计算受影响文件集合（meta / tags / items/YYYY-MM）
         ├─ Git Data API 原子提交（D11）：
         │    createBlob(每个文件) → createTree → createCommit → updateRef(带 CAS)
         ├─ 成功 → 清空这批 outbox、更新本地 blob sha / etag、角标变「已同步」
         └─ 失败 → 分类处理（422 走合并重试；5xx/网络走指数退避重试）
```

### 5.3 多设备并发（冲突路径）

```
设备 A 与设备 B 同时编辑
  └─ B 的 updateRef 因分支已前进而失败
  └─ B: pull() 拉回 A 的最新数据
      → 按 item 粒度 LWW 合并（merge.ts 纯函数）
      → 重放 B 的 outbox（本地未推送的修改优先级靠 updatedAt 判定）
      → 重新原子提交（最多 3 次，指数退避）
      → 仍失败 → 状态置 conflict，顶部横幅提示「有 X 条冲突待处理」+ 导出手动备份入口
```

## 6. 部署拓扑

| 项 | 值 |
| --- | --- |
| 前端地址 | `https://salenju.github.io/my-collector/` |
| Vite `base` | `/my-collector/` |
| 路由模式 | `createWebHistory('/my-collector/')` |
| SPA 兜底 | 构建后把 `index.html` 复制为 `404.html`（GitHub Pages 无服务端 rewrite） |
| PWA `scope` | `/my-collector/` |
| 部署触发 | push 到 `main` → `.github/workflows/deploy-web.yml` |
| Pages 配置前提 | 仓库 Settings → Pages → Source = **GitHub Actions** |
| 数据仓库可见性 | **必须 Private**；PAT 仅授权此仓库 |

> 子路径是本方案最容易踩坑的地方：`base`、router base、manifest `scope`/`start_url`、
> Service Worker `scope` 必须四处一致，否则会出现「页面能开但 PWA 装不上 / 路由 404」。已在 07 文档列为验收项。

## 7. 非功能指标

| 维度 | 目标 |
| --- | --- |
| 首屏（有本地缓存，弱网） | < 1s 可交互 |
| 首屏（无缓存，冷启动） | < 3s 渲染出列表（依赖 GitHub 响应） |
| 单次保存到远端可见 | ≤ 5s（含 2s 写去抖） |
| 前端产物（gzip） | 应用 shell < 200KB（不含按需加载的路由页） |
| GitHub API 用量 | 日常 < 200 请求/天（限额 5000/小时） |
| 单文件大小 | 每个分片 < 500KB（约 1000 条），超过则自动开新分片（按月天然满足） |
| 离线可用性 | 100% 核心功能（增/改/查）可离线完成 |
