## 1. 目标与非目标

**目标**

1. 在条目编辑器里**拖动或点击上传**照片，支持**直接粘贴截图**（C6 已确认进 v1，见 §9.1.1），支持**删除**（PRD 的两条硬要求）。
2. 图片与条目数据**同仓库、同权限、同版本历史**，不引入第二套凭据与运维对象。
3. 复用现有的「离线优先 + outbox + 一次原子提交」链路，图片不会出现「图没上去但条目记下了」。
4. 不破坏既有承诺：无服务器、无数据库、`git clone` 即完整备份、Git 历史可回滚。
5. 控制住两个真实成本：**GitHub 限流**与**仓库体积**。

**非目标（本期不做）**

- Chrome 扩展上传（下期；但 `core` 的接口本期就抽好）。
- 图片排序、图片标注、OCR / EXIF 信息提取。
- **物理删除图片 blob**（见 §7，Git 无法真正回收空间——这是机制决定的，不是没做）。
- Lsky/图床实现（只留 `AssetStore` 接口）。
- 图片作为独立记录（`type='image'`）——Q1 已明确为「条目附件」。

## 2. 决策摘要

| # | 决策 | 结论 | 理由摘要 |
| --- | --- | --- | --- |
| D15 | 图片存储位置 | 作为 blob 存入**同一个 GitHub 私有数据仓库**，路径 `data/assets/` | 零新基建、复用同一 PAT、随 Git 版本可回滚、隐私一致（§2.3） |
| D16 | 存储层抽象 | 抽 `AssetService`（stage / publish / resolve 三段），默认 `GithubAssetStore`，Lsky 留空实现 | 换后端不迁数据；但本期不为它引入运维成本（§5） |
| D17 | 寻址方式 | **内容寻址**：`sha = sha256(压缩后字节) 前 32 位`，文件名即 id | 天然去重、图片不可变→**冲突面为零**、可做缓存 key（§4.2） |
| D18 | 与条目的一致性 | 图片 blob 与条目 JSON 放进**同一次原子提交** | 保持「一次提交 = 数据一致」，杜绝半成功状态（§6.5） |
| D19 | **schemaVersion 升到 2** | `CURRENT_SCHEMA_VERSION = 2`，并做一次性 meta 回写，让旧客户端进入只读 | 旧客户端的 `normalizeItem` 会**静默抹掉 `assets` 字段**，这是真实的数据丢失路径（§4.3，**本文最重要的一条**） |
| D20 | 图片不进 JSON | `Item.assets[]` 只存元信息，绝不存 base64 | 沿用 02 文档 §2.6 已确立的原则；否则单条 item 会突破 8KB 建议值、diff 不可读 |

### 2.1 一句话方案

> 图片在上传时被压缩成 300–500KB 的 JPEG（外加一张 15–30KB 的缩略图），以**内容 sha 为文件名**写进 `data/assets/<前两位>/<sha>.jpg`，与条目 JSON 在**同一次 commit** 里提交；
> 渲染时通过 GitHub Contents API 的 raw 媒体类型**带鉴权取回字节**，缓存进 IndexedDB 并转成 `blob:` URL——因此图片既在私有仓库里，也能离线与秒开。

### 2.2 为什么限制在 GitHub 方案上是可接受的

**限流**：靠「缩略图 + 内容寻址 + IndexedDB blob 缓存」把它压到可忽略：

| 场景 | GitHub 请求数 |
| --- | --- |
| 新增 1 条带 3 张图 | 3 blob + 1 tree + 1 commit + 1 ref = **6** |
| 一次性新增 10 张图（同一批） | 10 + 3 = **13** |
| 首次浏览一屏 30 张缩略图 | **30**（懒加载，只加载视口内） |
| 再次浏览同一批 | **0**（IndexedDB 命中） |
| 一次 pull（含图片索引） | **不额外增加**——索引来自已有的 Trees 响应 |

额度 5000/小时。日常「记录 → 浏览」的消耗在几百次量级，余量充足。

**仓库体积**（按压缩后 400KB/张 + 缩略图 25KB/张估算）：

| 图片数量 | 原图 | 缩略图 | 合计 | 相对 GitHub 边界 |
| --- | --- | --- | --- | --- |
| 100 张 | 40 MB | 2.5 MB | ~43 MB | 无压力 |
| 500 张 | 200 MB | 12.5 MB | ~213 MB | 无压力 |
| 2 000 张 | 800 MB | 50 MB | ~850 MB | 接近建议上限 1GB |
| 5 000 张 | 2.0 GB | 125 MB | ~2.1 GB | 距 5GB 告警线仍有距离 |

结论：自用**几千张**是安全的。设置页会显示当前图片占用，超过 **800MB** 给出提示（§9.4）；真到上万张再考虑接图床，届时数据模型不用改。

另外应用**从不 clone 仓库**（走 Trees API 只取 path + sha），所以仓库变大对冷启动的成本只是那 1 个响应体变大；Trees 响应在约 3.3 万张图（10 万条目）时才可能被截断，并已有 `truncated` 告警兜底。

### 2.3 被否决的方案

| 方案 | 优点 | 被否的原因 |
| --- | --- | --- |
| **GitHub 私有仓库存 blob（采用）** | 零基建、同一 PAT、可回滚、隐私一致 | 需鉴权取图（§5.3）、占限流与体积（§2.2，可接受） |
| R2 + Lsky-Pro | 直链 + CDN，不占 GitHub 限流/体积 | Lsky 是 PHP + 数据库应用，直接推翻 README 首句「没有服务器，也没有数据库」；与 08 文档 §2.3「不把 Token 交给自建服务代管」冲突；为一个「方便记录信息」的小功能引入机器/域名/TLS/备份/安全更新的运维成本，投入产出比不成立。**保留为可选实现**（§5.4） |
| 纯 R2（前端直传） | 便宜、快 | 不成立：S3 兼容接口要 SigV4 签名，而本项目前端代码完全公开（08 文档首句），密钥放前端等于泄露。要落地必须先加一个签名层（Worker/Lsky），那就已经是「有服务端」了 |
| base64 塞进 `item` JSON | 请求最少 | 02 文档 §2.6 已否决：单条 item 会远超 8KB、文件体积不可控、diff 彻底不可读，且 JSON 会随每次编辑整体重写 |
| Git LFS | Git 专为大文件设计 | 免费额度仅 1GB 存储 / 1GB 流量/月；且浏览器端无法用 Contents / Git Data API 写 LFS 对象（需 git 客户端或 batch API），复杂度不划算 |
| 单独开一个**公开**图片仓库 | 可直接 `<img src>`、不占 API 限流 | 图片变公开，隐私破坏 |

## 3. 数据模型

### 3.1 `ItemAsset`

```ts
// core/src/model/types.ts
export interface ItemAsset {
  /** 内容 sha256 的十六进制前 32 位（128 bit）。既是去重键，也是仓库文件名 */
  id: string;
  /** 用户原始文件名，仅用于下载与展示（≤ 120 字符） */
  name: string;
  /** 压缩后的字节数 */
  size: number;
  /** 压缩后的像素尺寸：列表按此比例占位，避免图片加载完成后布局跳动（CLS） */
  width: number;
  height: number;
  /** 压缩后的 MIME：'image/jpeg' | 'image/png' */
  mime: string;
}
```

`Item` 增加一个可选字段：

```ts
export interface Item {
  // …既有字段不变…
  /** 附件图片（v2 新增）。顺序即展示顺序 */
  assets?: ItemAsset[];
}
```

**字段设计要点**

| 字段 | 为什么这样设计 |
| --- | --- |
| `id` = 内容 sha | 同一张图重复上传零成本（文件名相同 → 内容相同 → Git 无变化）；图片**永不修改**，所以永远不会产生冲突，**现有的 LWW + 墓碑合并逻辑一行都不用改** |
| `width` / `height` | 缩略图未加载完时用 `aspect-ratio` 占位。没有它，一屏图片加载完会把列表"顶下去"，体验很差 |
| `size` | 设置页统计占用、单条体积提示，都靠它；避免额外遍历仓库 |
| `name` | 只用于下载时的文件名与无障碍 `alt`；**不参与路径**（防止用户文件名里的特殊字符进入 Git 路径） |
| `mime` | 决定渲染方式与扩展名；只允许 jpeg/png（§6.1） |
| 不设 `thumb` 字段 | 缩略图与原件是 1:1 派生的，命名规则固定（`<sha>.thumb.<ext>`），存在与否不需要字段表达 |

### 3.2 数据仓库布局

```
my-collector-data/
├── README.md
└── data/
    ├── meta.json
    ├── tags.json
    ├── items/2026-10.json
    └── assets/
        ├── 3f/
        │   ├── 3f8a…c1.jpg          # 压缩后的原图
        │   └── 3f8a…c1.thumb.jpg    # 缩略图（列表专用）
        └── a7/
            ├── a70b…9e.png
            └── a70b…9e.thumb.png
```

**为什么分两级目录**：单目录堆几千个文件对 Git 与 GitHub 网页端都不友好；取 sha 前两位分桶，任何规模的分布都均匀。

**为什么缩略图沿用原图 sha 而不是自己的 sha**：缩略图是**确定的派生结果**（同样的参数必然得到同样的字节），1:1 对应原图，用原图 sha 加后缀最容易反查，也便于将来"清缓存时一起处理"。它在体积上是纯增量，不参与去重决策。

**路径规则**（全部由 `dataDir` 派生，不硬编码，与 `sync/paths.ts` 的既有约定一致）：

```ts
export function assetsPrefix(cfg: RepoConfig): string;                       // `${dataDir}/assets/`
export function assetPath(cfg: RepoConfig, id: string, ext: string): string; // `${prefix}${id.slice(0,2)}/${id}.${ext}`
export function assetThumbPath(cfg: RepoConfig, id: string, ext: string): string;
/** 从仓库路径反解 asset id；不是资产文件返回 null（pull 侧构建远端索引用） */
export function assetIdFromPath(cfg: RepoConfig, path: string): string | null;
```

`assetIdFromPath` 必须能区分「原图 / 缩略图」并正确剥离后缀，同时**忽略** `assets/` 下任何不符合 `<32位hex>.<ext>` 命名的手工文件（返回 `null`，不报错）。

### 3.3 ⚠️ schemaVersion 升到 2 与旧版本只读保护

**这是本文档最重要的一条决策，请重点评审。**

`normalizeItem()`（`model/guards.ts`）是**白名单式重建**——它 `return` 一个只含已知字段的新对象。因此一个**不认识 `assets` 的旧版本**在处理数据时的行为是：

1. `isItem()` 只校验已知字段，**不会因多出 `assets` 而拒绝**；
2. `normalizeItem()` 构造新对象 → **`assets` 被静默丢弃**；
3. `renderItemsFile()` 用归一化后的对象重写分片 → **提交后远端 JSON 里的 `assets` 永久消失**。

触发路径有两条，都很容易发生：

| 路径 | 后果 |
| --- | --- |
| 另一台设备/另一个浏览器标签页跑着旧版本（或 Service Worker 缓存了旧产物）→ pull 后编辑任意一条 → push | 该月分片里的**所有** `assets` 被抹掉 |
| 未重建的 Chrome 扩展用「直连提交」收藏一个链接 | `shared/collect.ts` 的 `readShard → parseItemsFile → normalizeItem → renderItemsFile` 走的是同一条路，**收藏一个链接就能抹掉该月全部图片引用** |

**对策（采用现成机制，零新增设计）**：把 `CURRENT_SCHEMA_VERSION` 从 1 升到 **2**。

- 新客户端写入的 `meta.json` 里 `schemaVersion = 2`；
- 旧客户端的 `isSchemaCompatible(2)` → `2 > 1` → **进入只读模式**（engine 的 `pushInternal` 在 `readOnly` 时直接 return），不会覆盖任何数据（02 文档 §4.3 原本就是为这种情况设计的）；
- 新客户端读旧数据（`1 <= 2`）→ 正常，且本次变更是**纯新增字段**，无需迁移（缺 `assets` 即视为空数组）。

**配套动作（必须做，否则门禁不生效）**：`meta.json` 只在设备名变化或初始化时被重写（`buildMetaFile`，由 `outbox.entity='meta'` 触发）。因此需要一个**一次性的「schema 升级」动作**：新版本启动时若本地记录的 `metaFile.schemaVersion < 2`，则入队一次 `entity='meta'` 操作并立即推送，把 `schemaVersion=2` 写到远端。

> 顺带说明：**Chrome 扩展必须与网页版同版本重建**（它 bundle 了同一份 core）。因为扩展走「直连提交」且**不检查 readOnly**（`shared/collect.ts` 没有这个判断），门禁拦不住它——所以更新顺序应为：先升级网页版 → 再 `pnpm build:ext` 重新加载扩展。这一条要写进 09 文档的变更说明与 AboutView 的帮助页。

**备选方案（本期不采用）**：让 `normalizeItem` **保留未知字段**（前向兼容）。它更彻底，但会让文件格式失去「白名单」的严格性，也可能把手工编辑注入的垃圾字段长期保留。列为 a2 讨论项，本期用 schema 门禁。

### 3.4 校验与归一化（`model/guards.ts` 变更）

```ts
export const LIMITS = {
  // …既有…
  assetsPerItem: 20,
  assetName: 120,
};
```

- `isItemAsset(v)`：`id` 必须是 `/^[0-9a-f]{32}$/`；`size` 为正整数且 ≤ 2MB；`width`/`height` 为正整数；`mime` 在 `['image/jpeg','image/png']` 内；`name` 为字符串。
- `isItem`：`if (v.assets !== undefined && (!Array.isArray(v.assets) || !v.assets.every(isItemAsset))) return false;`
- `normalizeItem`：
  - 保留 `assets`，**按 `id` 去重**、**按 `id` 升序排序**（保证输出稳定、diff 干净，与 `groupByShard` 对 items 排序的动机一致）；
  - 截断到 `LIMITS.assetsPerItem` 条、`name` 截断到 `LIMITS.assetName`；
  - 非法项**剔除并计入警告**（沿用「宁可少显示，也不让坏数据破坏缓存」）；
  - 旧数据无 `assets` → 不写该字段（**不是空数组**，避免无意义 diff）。

## 4. 本地存储变更（Dexie v2）

```ts
// core/src/store/schema.ts
export interface AssetRow {
  /** 主键：`${sha}:${kind}`，kind = 'original' | 'thumb' */
  key: string;
  sha: string;
  kind: AssetKind;
  mime: string;
  bytes: number;
  /** 压缩后的原图字节；缩略图行为 null（需要时按需重新生成） */
  blob: Blob | null;
  width: number;
  height: number;
  name: string;
  /** pending = 还没进过远端提交（**离线队列**）；uploaded = 已在远端 */
  status: 'pending' | 'uploaded';
  at: string;
  lastAccessAt: number;
}

db.version(2).stores({
  // v1 的 8 张表原样保留
  …
  assets: 'key, sha, status, at, lastAccessAt',
});
```

**为什么用一张表存「待上传对象」与「已下载缓存」**：两者的生命周期本来就重叠（上传成功后就地变成缓存），分两张表要处理搬迁与一致性。用 `status` 区分即可，代价是 LRU 淘汰必须**跳过 `status='pending'`**（待上传对象是用户数据，绝不能被淘汰）。

**远端图片索引不需要新表**：`RemoteSnapshot.files` 已经在本地镜像了「全仓库路径 → blob sha」，而 asset 的文件名本身就是其 id。因此：

```ts
// core/src/assets/index.ts
/** 从远端快照派生「远端已有哪些 asset」——不额外发任何请求 */
export function remoteAssetIds(snapshot: RemoteSnapshot, cfg: RepoConfig): Set<string>;
```

**其他表的变化**

| 表 | 变化 |
| --- | --- |
| `outbox` | `OutboxEntity` 增加 `'asset'`（`entityId` = asset id），用于离线排队与提交信息统计 |
| `drafts` | 编辑器草稿增加 `assetIds: string[]`，避免「拖了三张图、误关页面全丢」 |
| `settings` | 新增 `assets` 分组：`{ autoCompress, maxEdge, quality, cacheBudgetBytes }` |

## 5. 存储抽象：`AssetService`

图片的读、写、引用是三件不同的事，因此不做「一个大接口」，而是三段小接口——将来接 Lsky 时，只有 `publish` 与 `resolve` 需要换实现。

```ts
// core/src/assets/types.ts
export interface AssetService {
  /** ① 登记：压缩 → 计算 sha → 落本地 pending → 返回可直接写进 item.assets 的元信息 */
  stage(file: File, opts?: StageOptions): Promise<ItemAsset>;

  /** ② 发布：提交时把待上传对象并入本次原子提交；成功后标记 uploaded */
  collectPending(ids: readonly string[]): Promise<AtomicFileWrite[]>;
  markPublished(ids: readonly string[]): Promise<void>;

  /** ③ 解析：拿到可直接喂给 <img src> 的 URL（GitHub 实现带鉴权取字节 + blob 缓存） */
  resolve(asset: ItemAsset, variant?: 'original' | 'thumb'): Promise<string>;
  /** 引用计数减一；归零时 revokeObjectURL */
  release(url: string): void;

  /** ④ 维护 */
  sweepUnreferenced(): Promise<number>;   // 清理没有被任何条目引用、且尚未上传的对象
  cacheUsage(): Promise<{ bytes: number; count: number }>;
  clearCache(): Promise<void>;
}
```

### 5.1 `GithubAssetStore`（本期唯一实现）

`collectPending` 返回 `{ path, bytes }` 形式的二进制文件条目，直接交给 `GitDataApi.commitAtomic`；`resolve` 走「本地缓存 → 命中即 objectURL；未命中 → 拉取 → 写缓存 → objectURL」。

### 5.2 依赖注入位置

`createCollector()`（`core/src/index.ts`）里组装：

```ts
const assets = new GithubAssetStore({ db, github, getConfig: () => settings.repoConfig, getBudget: () => settings.assetsSettings.cacheBudgetBytes });
// 注入给 repository（stage/sweep）与 engine（collectPending/markPublished）
return { db, auth, github, sync, repo, settings, assets };
```

### 5.3 `resolve` 为什么必须经过鉴权（而不是直接给 `<img src>`）

数据仓库是 **Private**。对 `raw.githubusercontent.com/...` 的普通 `<img>` 请求不会携带 `Authorization` 头，结果必然是 401/404。所以：

```
resolve(asset, 'thumb')
 ├─ 命中本地缓存 → URL.createObjectURL(blob) → 返回（并 refcount++）
 └─ 未命中
     ├─ GET /repos/{owner}/{repo}/contents/{assetPath}?ref=main
     │   Header: Accept: application/vnd.github.raw        ← 关键：直接返回原始字节
     └─ → Blob → 写 assets 表（status='uploaded'）→ objectURL → 返回
```

**为什么用 `application/vnd.github.raw` 而不是默认的 base64 JSON**：

| | 默认 base64 JSON | `application/vnd.github.raw` |
| --- | --- | --- |
| 传输开销 | +33%（base64 膨胀） | 原始字节 |
| >1MB 限制 | 有（Contents API 不返回 `content`，需回落 Blobs API） | **无**，且支持 `Range`（将来可做渐进加载） |
| 解析 | decode → Uint8Array → Blob | 直接 `arrayBuffer()` → Blob |

注意：现有 `GhHttp.request()` 固定 `accept: application/vnd.github+json` 且一律 `.text()` + `JSON.parse()`。需要给它加两件事（§10.2）：
- `GhRequestInit.accept?: string`（覆盖默认 accept）；
- `GhRequestInit.responseType?: 'json' | 'bytes'`（`bytes` 时走 `arrayBuffer()`，不解析 JSON）。

**CSP**：`vite.config.ts` 的 `img-src` 目前是 `'self' data: https:`——**没有 `blob:`**。`blob:` URL 会被 `img-src` 拦截，导致图片全部不显示。必须显式加上：

```
img-src 'self' data: blob: https:;
```

（`connect-src` 已含 `https:`，上传与取字节不需要再改；Web Worker 由 `default-src 'self'` 覆盖，也不需要改。）
**这条必须用 `pnpm preview && pnpm smoke` 实测确认**——它属于「类型检查与构建都看不出来」的那类问题（参考 09 文档 §4.1 的 ref 单复数 bug）。

### 5.4 将来接 Lsky / 图床

只需新增一个 `LskyAssetStore` 实现同一接口：

- `stage` 完全相同（压缩与 sha 都在本地做，与后端无关）；
- `collectPending` 返回 `[]`（不走 Git 提交），改在 `markPublished` 里真正 POST 到 `POST /api/v1/upload`，把返回的 `url` / `thumbnail_url` 写入……**这里会暴露一个数据模型问题**：`ItemAsset` 里现在没有 URL 字段，因为 GitHub 方案里 URL 是可派生的。

处理方式（写在这里是为了让评审看到这个边界）：`ItemAsset` 增加一个**可选** `url?: string`（`GithubAssetStore` 永不写它，`LskyAssetStore` 写入直链）。`resolve` 在 `url` 存在时直接返回它。这样换后端不需要迁数据，只需给已存在的条目"回填 URL"。本期不实现，但**字段现在就预留**，避免将来改 schema 又要升一次版本。

## 6. 上传链路

### 6.1 压缩与缩略图

| 项 | 值 | 说明 |
| --- | --- | --- |
| 接受的上限 | 源文件 ≤ 20 MB / 张 | 超过直接拒绝并提示（避免解码一个 200MB 的图把内存打爆） |
| 最长边 | 2048 px | 默认「中」档；设置页可选 1600 / 2048 / 2560 |
| 质量 | 0.8 |  |
| 输出格式 | 源为 `image/png` → `png`；其余 → `jpeg` | PNG 通常带透明通道，转 JPEG 会让透明底变黑 |
| 体积阶梯 | `>800KB` → 质量降到 0.7 重编码 → 仍超 → 最长边降到 1600、质量 0.7 → 仍 `>1MB` → 拒绝并提示 | 保证单张可控，避免一张图吃掉几十 MB 仓库 |
| 缩略图 | 最长边 320 px，质量 0.7，格式同上 | 约 15–30 KB，列表专用 |
| 不放大 | 源比目标小时不放大 | 避免小图被插值糊掉且体积反而变大 |

**实现位置**：`core/src/assets/image.ts`（纯函数）+ `core/src/assets/worker.ts`（Web Worker 入口）。

**为什么必须放 Worker**：`createImageBitmap` + `OffscreenCanvas.convertToBlob` 的编码是重活，手机端压缩一张 4000×3000 的照片在主线程上会造成 0.5–1 秒的明显卡顿（拖拽上传时尤其致命）。Worker 里**只做「解码 → 缩放 → 编码」**并回传 `Blob`，IndexedDB 写入与 UI 状态仍留在主线程——这个边界最干净。

**EXIF 方向（必须处理，否则手机照片会躺倒）**：

```ts
const bitmap = await createImageBitmap(file, { imageOrientation: 'from-image' });
```

`'from-image'` 会把 EXIF 方向**烘焙进像素**。降级路径：若浏览器不支持带 options 的 `createImageBitmap`（或抛错），退回经典的 `<img>` + `canvas.drawImage`（浏览器对 `<img>` 会自动应用 EXIF）。

**HEIC 的坑**：iPhone 照片可能是 HEIC。Safari 能解码，Chrome 不能。iOS 通过 `<input type="file" accept="image/*">` 上传时系统通常会自动转成 JPEG，但**不能假设一定成立**——因此解码失败要给明确文案：「浏览器无法解码该图片（可能是 HEIC 格式），请先转换为 JPEG 后重试」，而不是抛一个原始异常。

### 6.2 登记（`stage`）

```
stage(file)
 ├─ 校验类型（image/*）与体积（≤20MB）→ 不合格立即拒绝
 ├─ Worker：解码（含 EXIF 方向）→ 缩放到最长边 2048 → 编码 → 得到原图 Blob
 ├─ Worker：再生成 320px 缩略图 Blob
 ├─ sha = sha256Hex(原图字节).slice(0, 32)
 ├─ 若 assets 表里 `${sha}:original` 已存在且 status='uploaded'
 │     → 直接复用（**同图重复上传零请求**），但仍要把元信息加进 item.assets
 ├─ 写 assets 表：`${sha}:original`（status='pending'，带字节）、`${sha}:thumb`
 └─ 返回 ItemAsset{ id, name, size, width, height, mime }
```

**sha256 怎么算**：`crypto.subtle.digest('SHA-256', bytes)`。`crypto.subtle` 只在**安全上下文**可用——`https:`（GitHub Pages、`localhost`）没问题；若有人用局域网 IP 的 http 打开开发服务器会不可用。降级：退回一个纯 JS 的 sha256（约 40 行，无依赖），保证功能可用。

### 6.3 与条目一起入队

```ts
// store/repository.ts
async function applyAssetChanges(itemId: string, next: ItemAsset[]): Promise<void>
```

`createItem` / `updateItem` 在**同一个 Dexie 事务**内完成三件事（沿用 §4.1 既有模式，保证「改了但没入队」不可能发生）：

1. 写 `items`（`assets` 排序去重后落库）；
2. 对**新增**的 asset id 写 `outbox`：`{ entity: 'asset', entityId: sha, action: 'upsert', at }`；
3. 对**被移除**的 asset id 调 `sweepUnreferenced()`：若它仍 `status='pending'` 且没有任何本地条目引用 → 删掉（避免用户拖错一张图就永远留一个待上传对象）。

> 图片的删除**不需要墓碑**：`item.assets` 数组变短本身就是"删除"这个动作，它随条目 JSON 走既有的 LWW 合并。这是「图片不可变 + 引用式」带来的红利——**冲突矩阵不需要新增任何一条**。

### 6.4 outbox 的优先级

`asset` 必须在 `item` **之前**被处理吗？不需要——两者在同一次提交里，Git 的 tree 是原子的。但 `collectPending(ids)` 需要知道"本次哪些 asset 是新的"，做法是：从本次 `ops` 里的 `entity='asset'` 取出 id，再与 `remoteAssetIds(snapshot)` 求差集（远端已有则跳过，既省请求也避免生成一个 tree 内容完全相同的空提交）。

### 6.5 原子提交（`pushInternal` 的变更）

```ts
// sync/engine.ts
private async renderAffectedFiles(ops, cfg): Promise<AtomicFileWrite[]>   // ← 返回类型放宽
```

返回类型从 `Array<{ path: string; text: string }>` 放宽为 `AtomicFileWrite[]`，其中：

```ts
// github/contents.ts
export type AtomicFileWrite =
  | { path: string; text: string }
  | { path: string; bytes: Uint8Array };
```

`gitData.commitAtomic` 只需在编码处分支（约 3 行）：

```ts
const content = 'text' in file ? encodeBase64Utf8(file.text) : encodeBase64Bytes(file.bytes);
```

**⚠️ 不能用 `encodeBase64Utf8` 编码二进制**：它内部是 `new TextEncoder().encode(input)`，把 JS 字符串按 UTF-8 编成字节——对二进制数据是**有损**的（任何 ≥0x80 的字节都会被篡改）。必须新增：

```ts
// utils/base64.ts（沿用既有的分块策略，避免 String.fromCharCode(...) 参数过多爆栈）
export function encodeBase64Bytes(bytes: Uint8Array): string;
export function decodeBase64Bytes(input: string): Uint8Array;
```

**请求数与顺序**：`N` 个新图片 = `N` 次 `POST /git/blobs`（沿用既有的 `mapLimit(files, 3, …)` 并发 3，且**每个 blob 是独立请求**，因此单次请求体始终只有几百 KB——这也是"不用一个大 JSON 塞所有图片"的另一个好处），外加 tree/commit/ref 各 1 次。

**失败重试的安全性**：提交是「先创建游离对象、最后一步才改分支」的原子操作（03 文档 §4.2），失败时分支未动；GitHub 对**相同内容**返回**同一个 blob sha**，所以重试重复创建 blob 不会污染仓库，也不会产生重复资产。

**提交信息**加一段统计：

```
sync: 1 条条目, 3 张图片, 0 个标签 [device:MacBook Chrome]

± item	9f2c…
+ asset	3f8a…c1（image/jpeg, 412KB）
```

### 6.6 批量上限

单条条目最多 **20 张**（`LIMITS.assetsPerItem`）。理由：一次提交的 blob 请求数 = 图片数，20 张 ≈ 20 请求 + 约 8–10MB 的 base64 上传；再往上不如让用户分条记录。超限在 UI 层直接拒绝并提示，不进入 `stage`。

## 7. 读取、缓存与删除

### 7.1 缓存策略

| 项 | 设计 |
| --- | --- |
| 缓存内容 | 原图 + 缩略图的 `Blob`，key `sha:kind` |
| 预算 | 默认 **200 MB**（设置页可调），超过则按 `lastAccessAt` 做 LRU 淘汰 |
| 例外 | `status='pending'` **永不淘汰**（是尚未上传的用户数据） |
| 持久化 | 首次上传图片时请求 `navigator.storage.persist()`，降低被浏览器清理的概率（失败不影响功能） |
| objectURL | 由 `assets/cache.ts` 统一管理：`resolve` 时 refcount++，`release` 时减一，归零才 `revokeObjectURL`。**组件卸载必须 release**，否则会内存泄漏并且 src 失效 |
| 懒加载 | 列表缩略图用 `IntersectionObserver`，只加载视口内（这是 §2.2 限流估算成立的前提） |

### 7.2 删除图片

| 层面 | 行为 |
| --- | --- |
| 条目引用 | 从 `item.assets` 移除 → 一次普通 `updateItem` → 随条目 JSON 走 LWW 合并传播到其他设备 |
| 仓库里的 blob | **保留**（见下） |
| 本地缓存 | 保留（其他条目可能引用同一张；LRU 会自然回收） |
| 待上传对象 | 若尚未上传且已无引用 → 立即删除（§6.3） |

**必须诚实告知用户的一件事：在 Git 里删除图片 blob 并不能真正回收空间。**

- 图片是内容寻址的，每张图在 Git 里**只有 1 个 blob、1 个版本**（不存在"改一次翻一倍"）；
- 但反过来，把 path 从 tree 里移除**只是让 HEAD 不再包含它**，历史提交里那个 blob 依然存在，仓库体积几乎不变；
- 真正回收只能靠**重写历史**（`git filter-repo` + force push），而那会打断所有其他设备的同步——本项目的设计前提（多端 + 非快进拒绝）与它直接冲突。

所以本期的「删除照片」= **解除引用**。帮助页必须写明这一点，否则用户会以为删了图仓库就变小了。

> a2 可做「清理未引用的图片」：扫描全部分片求出未被引用的 asset id，用 Git Trees API 的 `{ path, sha: null }` 删除条目并整片重写——机制与 D-13 的「清理墓碑」同构（独立 outbox 单元），但它只减小 HEAD 体积，**不减小仓库体积**，所以优先级低。

### 7.3 导出与备份

- 「导出全部 JSON」的产物里 `assets` 只含元信息，**不含图片字节**（图片本体在数据仓库里）。帮助页与导出提示要写明：JSON 备份 + 数据仓库才是完整数据。
- `git clone --mirror` 的备份建议（08 文档 §5.1）**依然成立且更完整**——它包含图片。
- a2 可选：导出时把图片打包进 zip。

## 8. 多端同步

| 环节 | 设计 |
| --- | --- |
| pull | **不下载任何图片字节**。从已有的 Trees 响应里筛 `assets/` 前缀条目构建远端索引（零额外请求），与本地 pending 求差集后把远端已有的标为 `uploaded` |
| pull（条目侧） | `item.assets` 随分片 JSON 正常合并；图片不可变 → 不产生任何新冲突类型 |
| pull（截断告警） | `listing.truncated` 时既有告警保留，追加一句："图片索引可能不完整，已存在的图片可能被重复上传（不产生新提交，但会多耗请求）" |
| push | §6.5 |
| 离线 | 条目与图片都在本地 pending（图片字节存在 `assets` 表），恢复网络后由同一次原子提交推上去 |
| 另一端 | pull 后 `item.assets` 立即出现（元信息来自 JSON），缩略图在进入视口时才按需拉取——**不会因为同步而批量下载图片** |
| 扩展 | 本期不涉及上传；但**必须与网页版同版本重建**（§3.3） |

**冲突矩阵（04 文档 §5.2）的变化**：**不新增任何一条**。图片不可变，冲突面为零；`item.assets` 是普通字段，`updatedAt` 的 LWW 已覆盖。

### 8.1 具体场景走查

| # | 场景 | 期望行为 |
| --- | --- | --- |
| A1 | 断网时给一条记录拖 3 张图 | 3 张立即显示（本地 objectURL），状态 `offline`；恢复网络后**一次提交**推上去 |
| A2 | 上传中途关掉页面 | 图片字节在 `assets` 表（pending），条目 `assets` 已落库，outbox 已入队；下次启动自动推送 |
| A3 | 手机与电脑同时给同一条记录加图 | 非快进 422 → 自动合并（LWW 取 `updatedAt` 较新者）；**图片不会互相污染**（各自的 blob 已在仓库里，被覆盖的一方只是引用消失，可再从 Git 历史找回） |
| A4 | 两端上传**同一张图** | 内容 sha 相同 → 文件名相同 → 第二次上传不会改变任何内容（甚至不产生 diff） |
| A5 | A 设备删图，B 设备正在看 | B 下次 pull 后 `item.assets` 变短，缩略图消失；B 本地缓存文件仍在（LRU 回收） |
| A6 | 旧版本客户端（含未重建的扩展） | `meta.json` 的 `schemaVersion=2` → 网页版旧客户端进只读；扩展走直连提交**不受门禁保护** → 因此必须先升级扩展（§3.3） |
| A7 | 数据仓库被手工改了图片路径 | `assetIdFromPath` 返回 null → 该文件不进入索引，UI 上表现为图片加载 404 → 降级为占位块并提示（不崩溃） |
| A8 | 单张图压缩后仍 >1MB | 逐级降质降尺寸，最终仍超限 → 拒绝该张并提示，**其他张正常上传** |

#### 9.1.1 粘贴上传的拦截规则（v1）

`AssetDropzone.vue` 在编辑器的 `<form>` 容器上监听 `paste`，但**只在应当接管时才拦截**——粘贴文字是主流程，绝不能被这个功能打断：

| 情形 | 处理 |
| --- | --- |
| 事件目标在 `input` / `textarea` / `[contenteditable]` 内 | **完全不拦截**（用户在「标题」「正文」里粘贴文字/链接是高频操作，`preventDefault` 会让它失效） |
| 剪贴板含图片（`clipboardData.files` 里的 `image/*`，或 `items` 里的 `image/png` blob） | `preventDefault()`，逐张走 `stage()`——与拖拽完全是同一条链路 |
| 同时含图片与文字 | 以图片为准并 `preventDefault()`，**不追加文字**（避免正文被塞进无意义的占位内容） |
| 只有文字 / 只有 URL | 不拦截，走浏览器默认行为 |

**文件名合成**：从剪贴板来的图片通常没有文件名（macOS 截图、网页右键「复制图片」）。`stage()` 需要一个 `name` 用于下载与 `alt`，缺失时合成为 `粘贴-YYYYMMDD-HHmmss.<ext>`——**扩展名由实际编码结果决定，不信任剪贴板给出的 mime**。

**多张**：`clipboardData.files` 可能是多项（一次复制多张图），按顺序逐张入列；命中 §6.6 的 20 张上限时，多余的直接拒绝并提示。

**为什么值得进 v1**：截图后直接粘贴是「记录碎片信息」最高频的路径之一——比「先存成文件、再拖进来」少两步，与 PRD 的诉求（方便记录有用的信息）直接对齐。

**实现提示**：把「是否接管」抽成一个纯函数 `shouldTakeOverPaste(target: EventTarget | null): boolean`（判定 `closest('input, textarea, [contenteditable]')`），与 DOM 操作解耦后可单测——粘贴拦截属于"写错了会打断主流程"的逻辑，值得有测试兜底。

### 9.5 帮助页 / AboutView

必须补的三句话（对应 08 文档 §4 的隐私边界表，需同步一行）：

1. 图片存在你自己的 GitHub 私有仓库里，和收藏数据同一个仓库、同一把令牌；查看时由浏览器带令牌取回（因此不是"公开图片链接"）。
2. **删除照片只是解除引用，仓库不会因此变小**（Git 历史里仍可找回；真正回收需要重写历史，本项目不做）。
3. 换设备/清缓存后，图片按需重新下载（有本地缓存）。

### 11.4 手工验收（需真实 PAT，与 09 文档 §六.1 的那轮验收合并做）

1. 拖 3 张手机照片上一条记录 → 到 GitHub 上确认 `data/assets/` 生成 6 个文件（3 原图 + 3 缩略图），提交只有一次；
2. 用另一台设备/浏览器拉取 → 缩略图正常显示 → 点开大图正常显示；
3. 断网加图 → 恢复后自动推送；
4. 移除一张图 → 远端 JSON 的 `assets` 少一条；
5. 用**旧版**网页产物（本地 `git stash` 出旧构建）打开 → 顶部出现只读横幅，且**不覆盖**任何数据；
6. 检查 `chrome://extensions` 里的扩展是否为同版本重建（A6）；
7. **粘贴**：在「正文」框里粘贴一段文字 → 正常插入文本、**不触发图片上传**；在编辑器空白处粘贴一张截图 → 作为图片入列，文件名被合成为 `粘贴-YYYYMMDD-HHmmss.<ext>`；再粘贴一张同名文件 → 因内容 sha 相同而**不产生新的上传**。

## 12. 风险登记

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 旧客户端静默抹掉 `assets` | **数据丢失（高）** | schemaVersion 升 2 + 一次性 meta 回写 + 旧客户端只读；扩展必须同版本重建（§3.3）。已列为本文第一优先级 |
| CSP 未放开 `blob:` | 图片全部不显示 | 显式加 `blob:`，并用冒烟测试验证（§5.3、§11.3） |
| 二进制误用 `encodeBase64Utf8` | 图片损坏（高，但可被测试覆盖） | 新增 `encodeBase64Bytes` 并有 1MB 随机字节往返测试（§11.1） |
| 每张图首次查看 = 1 请求 | 限流 | 缩略图 + 懒加载 + IndexedDB 缓存（§2.2 已有估算） |
| 仓库体积增长 | 超 5GB 被 GitHub 限制 | 压缩 + 缩略图 + 设置页占用提示（800MB 阈值）+ 迁移到图床的路径已留（§5.4） |
| 手机端压缩卡顿 | 交互体验 | 放 Web Worker；只有解码/缩放/编码在 Worker 里 |
| HEIC 无法解码 | 上传失败 | 捕获并给明确文案（§6.1） |
| `objectURL` 泄漏 | 内存增长、src 失效 | 统一 refcount + 组件卸载 release（§7.1） |
| Trees 响应变大 | 冷启动 payload | 数千张仅数百 KB；截断有告警兜底（§2.2、§8） |
| `crypto.subtle` 在非安全上下文不可用 | 局域网调试时上传失败 | 纯 JS sha256 降级（§6.2） |
| 用户以为删图能省仓库空间 | 预期错位 | 帮助页明确说明（§9.5） |
| 粘贴上传打断正常的文本粘贴 | 高频操作被打断 | 只在事件目标不属于 `input` / `textarea` / `[contenteditable]` 时接管（§9.1.1） |

## 14. 评审结论（已拍板）

> **2026-10-07 评审结论**：除 C6 外全部采用方案默认值；**C6 改为 v1 必做**（设计见 §9.1.1）。

| # | 事项 | 结论 | 影响 |
| --- | --- | --- | --- |
| C1 | 每条最多 20 张 | **20** | 单次提交的请求数与上传体积上限 |
| C2 | 单张源文件上限 | **20 MB** | 拒绝阈值；太松会解码爆内存，太紧会拒掉相机原图 |
| C3 | 压缩目标上限 | **800 KB**（超过则降质降尺寸，仍超 1MB 则拒绝） | 直接决定仓库能用多久 |
| C4 | 尺寸/画质默认档 | **2048 px / 0.8** | 画质与体积的取舍 |
| C5 | 本地图片缓存预算 | **200 MB** | 占用磁盘 vs 重复下载 |
| C6 | 是否 v1 就做「粘贴上传」 | **是，进 v1**（见 §9.1.1） | 截图后直接粘贴是碎片记录的高频路径，与 PRD 诉求直接对齐 |
| C7 | 空仓库/未初始化时能否加图 | **能**（图片与条目一起等初始化后推送） | 与现有"未配置 Token 也能记录"的体验保持一致 |
| C8 | 设置页占用阈值提示 | **800 MB** | 提醒用户考虑迁移到图床的时机 |
