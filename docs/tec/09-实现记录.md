### 4.1 测试抓到的真实缺陷（已修复）

**`PATCH /git/refs/...` 被写成了 `/git/ref/...`（单数）**。
GitHub 的读接口是 `GET /git/ref/{ref}`（单数），写接口是 `PATCH /git/refs/{ref}`（复数）。
最初两者共用一个路径构造函数，导致**所有推送都会 404**。
这个 bug 在类型检查与构建阶段完全看不出来，只在 engine 集成测试里暴露。
修复：拆成 `readRefPath()` / `updateRefPath()` 两个方法，并在注释里写明差异。

同时发现第二个缺陷：`handleSyncFailure` 对 `not-found` 这类不可重试的错误只记录 `lastError` 而
不改变状态，界面会一直停在「同步中」。已改为置为 `error` 终态。

## 五、设计偏离记录

### D-01 · meta.json 不再承载分片清单与 blobSha（已回写 02 / 03 文档）

**原设计**：`meta.json` 保存 `shards[{ path, month, count, blobSha }]` 与 `tagsSha`，
用 blobSha 比对来跳过未变更文件。

**问题**：`meta.json` 与各分片文件属于**同一次提交**，它的内容里不可能包含本次提交后各分片的新 blob sha
（写入前还不知道），形成循环依赖。

**改为**：用 **Git Trees API** 一次请求拿到全仓库文件的 `path + sha`（`GET /git/trees/{branch}?recursive=1`，
响应里的 `sha` 即根 tree sha，可直接作为 `base_tree`）。于是：

- 变更检测 = 「远端 sha ≠ 本地 fileCache.sha」，比原方案更省请求（原方案需要逐文件条件请求）；
- `meta.json` 只保留不会自指的字段：`schemaVersion` / `createdAt` / `tokenExpiresAt` / `deviceNames`；
- `lastSyncAt` / `lastDeviceId` 属于设备本地状态，移出远端（存在本地 settings）。

**顺带收益**：meta.json 不再需要在每次推送时重写，提交更干净。

### D-02 · 不使用 `@octokit/*`，改为手写 fetch 薄封装

**原设计**（03 文档 §2）用 `@octokit/core` + `plugin-retry`。

**改为**：`github/http.ts` 手写（约 160 行）。理由：

1. 全项目只用 10 个端点，`@octokit/rest` 的收益为零；
2. 本方案强依赖 `If-None-Match` / `x-ratelimit-*` / `retry-after` / 状态码到语义的映射，
   手写比在 SDK 之上再加一层适配更直接、更可控；
3. 少一个运行时依赖（08 文档 §6 的依赖克制原则），产物更小。

错误语义化（`GhErrorKind`）与重试策略完全按 03 文档 §2 保留，且把重试交给同步引擎而非 SDK。

### D-03 · 新增本地 `RemoteSnapshot`（03 / 04 文档的补充）

本地 `meta` 表中缓存 `{ commitSha, treeSha, files: {path: sha}, fetchedAt }`。
用途：① 作为 `expectedParentSha` 做快速 CAS 预检；② 提供 `base_tree`；
③ 推送成功后增量更新，避免每次推送都多发一轮请求。

### D-04 · 给 `Tag` 增加 `updatedAt` 与必需的 `deletedAt`（已回写 02 文档）

原 Tag schema 只有 `createdAt`，无法表达「两台设备同时改标签」「删除标签」的冲突裁决。
现在标签与条目共用同一套 LWW + 墓碑合并逻辑，避免"另一端删除的标签被本地复活"。

### D-05 · `mergePolicy` 的语义澄清

设计文档写的「删除优先 / 编辑优先」在实现中落为：

- `delete-wins`（默认）：只要一侧是墓碑就删除生效，**不看时间戳**；
- `edit-wins`：不做墓碑特判，纯按 `updatedAt` 裁决（删除可能被更晚的编辑覆盖回来）。

设置页已用文案说明这一细节，避免用户误解为"时间戳规则会被关闭"。

### D-06 · 图标库换成 `@lucide/vue` + 本地类型 shim

`lucide-vue-next` 已被上游标记为 deprecated（提示改用 `@lucide/vue`）。
但 `@lucide/vue@1.x` 的 `package.json` 没有 `types` 字段也没有 `exports` 映射，
`moduleResolution: bundler` 找不到它的 `.d.ts`。
因此在 `packages/web/src/types/lucide.d.ts` 里补了一份**只包含本项目实际用到图标**的最小声明，
待上游补齐类型后删除即可。

### D-07 · TS 配置未启用 `exactOptionalPropertyTypes`

`tsconfig.base.json` 启用了 `strict` / `noUncheckedIndexedAccess` / `noUnusedLocals` 等，
但**没有**启用 `exactOptionalPropertyTypes`：它与 Vue 的 `defineProps`/`withDefaults`
组合会产生大量噪声报错，收益不足以抵消维护成本。

### D-08 · CSP 的取舍（已回写 08 文档）

- 不在 meta 中下发 `frame-ancestors`（meta 形式会被浏览器忽略，且每次加载都会打一条 console error）；
- `connect-src` 放开为 `https:`，这是为了让「自建元信息抓取代理」（06 文档 §4.5）可用。
  真正的 XSS 边界是 `script-src 'self'`，它保持严格。
- CSP 只在**生产构建**注入（开发时 Vite 的 HMR 需要内联脚本与 ws 连接）。

### D-09 · 允许在「非空仓库」上初始化（已回写 02 文档）

**原设计**（03 文档 §4.4）：初始化的前提是「仓库为空」，因此 `initializeRepo` 在检测到已有提交时直接抛错
「数据仓库已有提交，无需初始化」。

**问题**：这是条**死路**。GitHub 新建仓库默认会勾选 "Add a README"，于是第一次进设置页会看到
「仓库尚未初始化 → 初始化数据仓库」的引导（因为 `initialized` 的判据是 `data/meta.json` 是否存在），
点下去却被「已有提交」挡住，而 UI 里没有任何地方告诉用户要先去删掉 README。

**改为**：判据从「仓库是否为空」改为「**是否已存在 `data/meta.json`**」。
已有提交时把 `head` 传给 `commitAtomic`，在既有 tree 上增量提交。

配套规则：**初始化时已存在的同名文件一律跳过、绝不覆盖**（`README.md`、`data/tags.json` 等）。
被跳过的文件会作为告警显示在同步状态面板里（"已保留仓库中已有的文件，未做覆盖：…"），
且只有真正写入了 `tags.json` 时才会把默认标签落到本地。
同时修正报错文案（明确提示"如需重建请先删除 `data/` 目录"）。

**教训**：写前置条件校验时要检查它会不会把用户困住——尤其是当这个条件由平台的默认行为触发时。

### D-10 · PWA 刻意**不**缓存 GitHub API 响应

**原设计的暗示**（01 文档「离线可用性」、AI 方案 §7「本地缓存优先」）容易让人顺手把 API 请求也加进运行时缓存。
实现时明确**不加** `runtimeCaching`：

如果离线时由 Service Worker 用缓存的 API 响应「假装成功」，同步引擎会认为刚刚拉到了最新的远端，
于是拿着**过期的远端数据**去做冲突合并——这比直接失败更危险（可能把别处的删除/修改判成"无变化"）。
正确行为是让请求失败 → 引擎进入 `offline` 状态 → 数据一律来自 IndexedDB。

**结论**：SW 只预缓存应用外壳（35 个文件 / 484KB），数据能力完全交给 IndexedDB + outbox。

### D-11 · 给 `packages/core` 加 `sideEffects: false`，让扩展能剔除 Dexie

扩展只用到 core 的「GitHub 读写 + 分片渲染 + 校验」这些纯逻辑，不需要 IndexedDB。
但 core 的入口是 barrel（`index.ts` 里 `export * from './store/schema'`），
Rollup 无法判断该模块有无副作用，于是把 Dexie 一并打进了扩展：

| | 优化前 | 优化后 |
| --- | --- | --- |
| 扩展共享 chunk | 181.8 KB（gzip 65.5 KB） | **83.8 KB（gzip 32.6 KB）** |

在 `packages/core/package.json` 声明 `"sideEffects": false` 后即可安全剔除（core 内没有任何模块级副作用，
也不含 CSS）。这是比"拆分 subpath exports"更省事的做法，且对网页端无影响。

### D-12 · PNG 图标用脚本生成，不引入原生图像依赖

PWA 可安装性需要 192px+ 的 PNG，Android 需要 maskable 版本，iOS 需要 apple-touch-icon。
只为生成 7 张图而引入 `sharp` / `canvas`（原生模块，CI 里还要装系统库）不划算。

因此写了 `scripts/gen-icons.mjs`：用 Node 内置 `zlib` 手写 PNG 编码（约 60 行），
把「圆角方块 + 八角星」用 3×3 超采样光栅化，输出 web 与扩展两套图标。
产物已提交，改图标时跑一次 `pnpm icons` 即可。

### D-13 · 「清理墓碑」走独立的分片重写单元（已回写 02 / 04 文档）

**原实现的缺陷**（04 文档 §4.2 的空白）：`purgeItem` / `purgeTombstones` 只做**本地物理删除**，
既没有写 outbox 也没有触发推送，而 `pushInternal` 在 outbox 为空时直接返回。
后果是双向的：

1. 远端 `data/items/*.json` 永远不会瘦身，墓碑永久留在文件里（设置页文案承诺的 commit 不存在）；
2. 下一次 pull 时，远端这条"本地已没有"的记录会走 `!local && remote` 分支被**拉回本地**，
   等于清理白做（此时若再 push，还会把它重新写回远端）。

**改为**：新增一种待推送单元 `outbox.entity='shard'`（`entityId='YYYY-MM'`），
`purgedIds` 记录被物理移除的条目 id（`replaceOps` 的覆盖语义在这里必须改成**取并集**，
否则同月分两次清理会丢掉先登记的那批）。`renderAffectedFiles()` 据此整片重写该月分片；
`pull` 侧把 outbox 里的 `purgedIds` 交给 `merge()`，命中时不采纳远端那条（记 `reason='purged'`）。

**为什么不是"整片忽略远端"**：那样会让另一台设备在该月的新记录在随后的整片重写里被静默丢掉。
只拦被清理的那个 id，才能既让清理生效、又不误伤并发写入。

**验证**：`engine.test.ts` 新增 3 例（跨月重写只影响受影响分片、同月多次清理取并集、
清理后先 pull 不复活），并做了反向验证——把修复回退后这 3 例全部失败。

### D-14 · 扩展的"右键/快捷键"从浮窗改为 Chrome 侧边栏（已回写 06 文档 §5.6）

**原设计**（06 文档 §5.3）：右键菜单与 `Alt+Shift+S` 用 `windows.create({type:'popup'})` 开一个
420×620 的独立浮窗。实际用起来每次都是"又开了一个窗口"，切页即丢、还要手动关。

**改为**：Chrome 原生侧边栏（`side_panel` + `sidePanel` 权限，`minimum_chrome_version` 已是 116）。
停靠当前窗口右侧，切标签页/刷新都不关闭。三个入口重新分工：工具栏图标仍走 `popup.html` 轻量浮窗
（`default_popup` 与 `setPanelBehavior({openPanelOnActionClick})` 互斥，保留 popup 就不设该行为），
右键菜单与快捷键走侧边栏。表单抽成 `shared/CollectForm.vue` 由两个外壳共用，`?quick=1` 浮窗路径与
`shared/params.ts` 一并下线。

**两个约束（写进 06 §5.6）**：
1. `sidePanel.open()` 只能待在用户手势的同步路径上（前面不能 `await`），所以 SW 是"先开面板、
   再异步 `readTab`"，页面信息经 `chrome.storage.session` 交付；
2. `chrome.sidePanel` 没有 close API，保存成功后面板不会（也无法）自动关闭。

**判定**：不为"跟随当前标签页"申请 `tabs` 权限（06 §5.6.1 记录了三个选项与理由）——
`activeTab` 授权只覆盖触发扩展的那个标签页，跟随必须加权限，收益不抵权限提示的心理成本。

**顺带的行为变化**：草稿从"无归属"改为**按 URL 归属**（`Draft.url`）。面板会长时间开着，
不加归属的话，为 A 页面存下的草稿会被套到 B 页面上。

### D-15 · 图片压缩先跑在主线程，暂不放进 Web Worker（偏离 10 文档 §6.1）

**原设计**：把「解码 → 缩放 → 编码」放进 Web Worker，理由是主线程压缩一张 12MP 照片
会有 150–400ms 的可感知停顿。

**改为**：v1 跑在主线程（`assets/codec.ts`），`OffscreenCanvas` 优先、DOM canvas 兜底。

**理由**：`ImageCodec` 的接口本身就是异步的（`open()` → `DecodedSource.encode()`），
换成 Worker 实现是 `codec.ts` **文件内部的替换**，调用方（`assets/image.ts`、`assets/githubStore.ts`）
一行都不用改。而 Worker 这条路径在当前环境里**无法被自动化验证**：单测跑在 Node 里、
冒烟测试只检查渲染与 console 错误，都不足以覆盖"消息协议 + 传输 + 生命周期"。
用一个不可验证的 Worker 换掉 300ms 的停顿，风险收益不划算。

**后续**：真机上如果"添加大量图片时明显卡顿"，再按下面的形状替换即可——
`new Worker(new URL('./worker.ts', import.meta.url), { type: 'module' })`，
Worker 内只做解码/缩放/编码并回传 `Blob`，IndexedDB 与 UI 状态仍留在主线程。

### D-16 · `CURRENT_SCHEMA_VERSION` 升到 2，并强制一次 meta 回写

**背景**：`normalizeItem()` 是白名单式重建——它 `return` 一个只含已知字段的新对象。
所以**不认识 `assets` 的旧客户端**在处理数据时：`isItem()` 不拒绝 → `normalizeItem()` 静默丢弃
→ `renderItemsFile()` 重写分片时把该月**所有**图片引用抹掉。

两条触发路径都很容易发生，第二条尤其隐蔽：

1. 另一台设备/另一个标签页跑着旧产物（或 SW 缓存了旧 chunk）→ 编辑任意条目 → push；
2. **未重建的 Chrome 扩展**：`shared/collect.ts` 的
   `readShard → parseItemsFile → normalizeItem → renderItemsFile` 是同一条路，
   **收藏一个链接就能抹掉该月全部图片引用**。

**改为**：`CURRENT_SCHEMA_VERSION = 2`，并新增 `ensureSchemaVersion()`——
`pull()` 结束时若发现远端 `meta.json` 的版本更低，就入队一次 `entity='meta'` 提交把它推到 2。
旧客户端随后读到「远端 2 > 本地 1」即进入只读模式（`pushInternal` 直接 return），不再覆盖数据。

**为什么必须主动写那一次 meta**：`meta.json` 只在设备名变化或初始化时被重写。
如果只是"新版本自己知道 v2"，远端仍然是 1，旧客户端的门禁**根本不会触发**。

**⚠️ 已知缺口**：扩展走「直连提交」且**不检查 `readOnly`**（`shared/collect.ts` 没有这个判断），
所以门禁拦不住它。更新顺序必须是：**先升级网页版 → 再 `pnpm build:ext` 重新加载扩展**。
这一条同时写进了「关于」页与 10 文档 §3.3。

**验证**：`engine.assets.test.ts` 有 4 例覆盖（入队并推到 2、已是 2 时不重复入队、
远端更高时只读且不写任何东西、以及一条"只读门禁是挡住旧客户端抹掉 assets 的唯一防线"的回归）。

### D-17 · 笔记正文支持 Markdown：自建渲染器，不引第三方库（已回写 05 §4.3.1 / 08 §3.1）

**需求**：新建页「笔记」模式的内容框要能写 Markdown，详情页要按 Markdown 展示。

**原设计**（08 文档 §3.1 旧表述）：v1 备注是纯文本；要做 Markdown 必须"先 sanitize"，
列为 a2 默认关闭。现在这条约束被替换为更严格的一条——**渲染器自建、输出端白名单**。

**为什么不用 marked/markdown-it + DOMPurify**：
1. 它们把「用户输入 → HTML」这一步交给了第三方，安全性依赖 sanitizer 的版本与配置；
   自建渲染器在拼接 HTML 时就把所有文本 `escapeHtml`，源文本里的 `<script>`、`onerror=`
   只会变成可见字符，**根本不存在注入面**，也就不需要运行时 sanitizer。
2. 保持零依赖：`markdown` chunk gzip 约 3.2KB，且不新增供应链风险与 CSP 约束。
3. 副作用是解析范围可控——只实现 GFM 常用子集（标题/列表/任务列表/引用/表格/代码块/链接/图片/
   删除线/分割线/转义），不做 HTML 块透传、不做脚注、不做公式，避免"看起来支持其实半残"。

**边界（有意为之）**：链接 `http/https/mailto`、图片仅 `https`（与 CSP `img-src` 对齐）；
不合法的地址只保留文字、不输出 href；外链一律 `target="_blank" rel="noopener noreferrer"`。
链接类型的「备注」仍走纯文本，避免用户只想写两句话却被格式化。

**验证**：`packages/web/src/utils/markdown.test.ts` 25 例（块级/行内/注入/健壮性/纯文本摘要），
`pnpm test` 全绿；`pnpm -F @my-collector/web typecheck`、`pnpm build` 通过。

### D-18 · 灯箱用「布局尺寸缩放」而不是 `transform: scale`（已回写 10 文档 §9.3）

**问题**：灯箱原来只有 `object-contain`，一张 1080×10800 的长截图被压进 ~700px 高的窗口后
宽度只剩 70px，等于看不了。

**做法**：给 `<img>` 直接按 `原图尺寸 × 比例` 定宽高，而不是套 `transform: scale()`。
原因很实际——`transform` 不改变布局，滚动容器的 `scrollWidth/scrollHeight` 不会跟着变，
长图放大后**滚不到下面的内容**；改布局尺寸后滚动条自然变长，浏览器原生滚动/惯性/双指捏合都能正常用。

配套的取舍：
- 默认视图按高宽比选（≥2.5 视为长图 → 适应宽度），长图打开即是"铺满宽度、上下滚"；
- 普通滚轮留给滚动（长图必须能滚），`Ctrl|⌘ + 滚轮` 才缩放——桌面端这是地图类应用的通用心智；
- 触屏单指走原生滚动、双指由 `touchmove` 捏合缩放（容器 `touch-action: pan-x pan-y`，避免缩放整个页面）；
- 鼠标放大后按住拖动平移；拖拽结束浏览器会补一个 click，用 `panMoved` 标记拦住它，否则"拖完就关灯箱"；
- 算术（适应换算/步进/夹取/指针锚点滚动补偿）抽到 `utils/zoom.ts`，纯函数、可单测。

**顺带修的坑**：`src/types/lucide.d.ts` 是只列本项目用到图标的最小 shim（见 D-06），
新增 `ZoomIn` / `ZoomOut` / `MoveHorizontal` 时**必须同步加进去**，否则类型检查报
"has no exported member"（运行时有、类型没有，容易误判成上游打包问题）。

**验证**：`pnpm -r typecheck`、`pnpm test`（238 例，含新增 `utils/zoom.test.ts` 16 例）、
`pnpm build`、`pnpm build:ext`、`pnpm preview` + `pnpm smoke`（6 条路由无 console 错误）全绿；
另用一个临时页面在无头 Chrome 里实测：长图默认 105%（可滚动）、「窗口」→7%（无滚动）、
`+`/`-` 步进、双击回适应、鼠标拖拽 `scrollTop` 0→170 且未误关、`Ctrl+滚轮` 105%→165%。

### D-19 · 小于 1.5MB 的图不压缩、原样入库（已回写 02 / 10 文档）

**问题**：`autoCompress` 默认开启，于是**任何**图上传后都会被重新编码成 2048/0.8。
一张 400KB 的截图本来很清楚，压完文字边缘发虚；一张 900KB 的 PNG 截图甚至可能被转码后更糊。
省下的体积很有限，画质损失却是每天都能看到的。

**做法**：`ASSET_LIMITS.passthroughBytes = 1.5MB`，`originalPassthroughMime()` 判定后直接存源字节
（不缩放、不重编码）。两条边界：

1. **只放过 JPEG / PNG**。仓库的文件名与 mime 只认这两种（`extFor` / `mimeForExt` / guards 的白名单），
   把 webp / gif / heic 原样存下来会变成"打不开的文件"，所以这些格式仍然转码——对它们来说"不压缩"反而更糟。
   将来若要真正支持 webp，得同时改 `ImageMime`、`extFor`、guards 白名单，属于 D-16 那类要升 schema 的改动。
2. **`maxStoredBytes` 必须 ≥ `passthroughBytes`**（两个常量相邻放着，`image.test.ts` 断言了这条不变式），
   否则原样保存的小图会被 `stage` 以"超过单张上限"拒掉。这次把上限从 1MB 同步放宽到 1.5MB。

**兼容性代价（记在这里，别再踩）**：入库上限从 1MB 放宽到 1.5MB 之后，
**仍是旧版本（≤1MB 校验）的设备**拉到这类条目时，`normalizeItem` 会把该 asset 静默丢掉，
它下一次编辑并推送就会把引用从分片 JSON 里抹掉（图片本体仍在仓库，可从不 Git 历史找回）。
这一条刻意**没有**升 `CURRENT_SCHEMA_VERSION`：升版本会让所有旧设备进只读，代价大于收益；
实践办法是「所有设备更新后再传大于 1MB 的图」。若将来真的踩到，再按 D-16 的方式升到 v3。

**验证**：`image.test.ts` 新增 5 例（小 jpeg / 小 png 字节完全一致、等于阈值仍压缩、小 webp 仍转码、
`maxStoredBytes ≥ passthroughBytes`），`pnpm test` 246 例全绿；`typecheck` / `build` / `build:ext` 通过。
另在无头 Chrome 里用真实 canvas 编解码器跑了一遍 `stage()`：932KB 的 PNG → 932KB **字节完全一致**、
385KB 的 JPEG → 字节完全一致、6.08MB 的 JPEG → 656KB（1600×1067，阶梯压到第三档）。

## 六、已知缺口与下一步

按优先级排列：

1. **用真实 PAT 跑一遍手工验收**（唯一还没做的关键验证）：初始化 → 新增 → 手机/另一台浏览器拉取 →
   断网记录 → 恢复联网 → 清理墓碑后到 GitHub 上确认分片文件真的变小。上面所有验证走的是假 GitHub 与无头浏览器，
   真实网络路径（含代理、CORS、限流头）只在实物上才能确认。验收清单见 07 文档 §4.3、04 文档 §8，
   **图片部分另加 10 文档 §11.4 的 7 步**（拖 3 张手机照片 → 确认 `data/assets/` 生成 6 个文件且只有一次提交；
   另一台设备缩略图与大图都正常；断网加图后恢复；正文里粘贴文字不被拦截、粘贴截图能入列；旧版产物进只读）。
2. **GitHub Actions 上线（M6）**：两个 workflow 已就绪，需要在 GitHub 上把 Pages Source 设为 **GitHub Actions**；
   并通过 `git tag ext-v0.1.0` 触发一次扩展打包，确认 Release 附件可用。
3. **JSON 导入 / 浏览器书签导入（M6）**：导入按「合并」语义实现（复用 merge 逻辑），书签导入解析 Netscape HTML。
4. **扩展的静默保存（体验补强）**：目前 `Alt+Shift+S` 与右键都要经过一个小窗口。
   若追求真正的"一键"，可在 background 里直接提交（复用 `shared/collect.ts`）并只用 badge 反馈成功/失败。
5. **扩展与网页版令牌一键同步（a2）**：manifest 里已声明 `externally_connectable`，
   background 也已接好 `onMessageExternal` 的 ping 分支，只差网页版侧发起 `chrome.runtime.sendMessage`。
6. **iOS 的分享替代方案（体验补强）**：帮助页目前只写了「iOS 不支持 share_target」，
   可以直接给出一个 iOS 快捷指令的配置步骤（打开 `/new?url=...`）。
7. **列表体验补强**：键盘导航（j/k/e/a/d）、虚拟滚动、连续记录模式。
8. **扩展打包体积**：当前共享 chunk gzip 32.6KB（已剔除 Dexie），如需进一步减小，
   可给 core 拆 subpath exports，让扩展只引 `@my-collector/core/github` 这一层。

## 七、给下一次对话的提示

- 所有数据层逻辑只在 `packages/core`，UI 不直接碰 Dexie 或 `fetch`；新增功能请沿用 `repository` / `engine`。
  扩展走的是「直连提交」（`shared/collect.ts`），刻意不做完整离线队列——改它之前先读 06 文档 §5.3 的理由。
- **图片相关的硬规则**（详见 10 文档 §6.5 / §7.1）：
  图片字节一律经 `collector.assets`，UI 不直接 `fetch` GitHub；
  **二进制必须用 `encodeBase64Bytes` / `decodeBase64Bytes`**——用 `encodeBase64Utf8` 会篡改 ≥0x80 的字节、图片必然损坏；
  `resolve()` 拿到的 objectURL 必须成对 `release()`，否则内存不回收且 URL 会失效；
  图片**不要单独提交**，它必须与条目 JSON 在同一次 `commitAtomic` 里（否则会出现半成功状态）。
- 改数据结构务必同步 `02-数据模型与存储.md` 与 `guards.ts` 的校验/归一化（否则旧数据会被静默跳过）。
  **给 `Item` 加字段尤其危险**：`normalizeItem` 是白名单式重建，旧版本会把不认识的字段**静默丢掉**并在下次推送时写回去。
  加字段就必须按 D-16 升 `CURRENT_SCHEMA_VERSION` 并让 `ensureSchemaVersion()` 把版本写到远端；
  同时别忘了**重新构建 Chrome 扩展**（它不受只读门禁保护）。
- 提交前请跑：`pnpm -r typecheck && pnpm test && pnpm build && pnpm build:ext`；
  涉及界面或 PWA 的改动再加一轮 `pnpm preview` + `pnpm smoke`。
- 涉及 GitHub 端点的改动，请在 `packages/core/src/testing/fakeGithub.ts` 中补上对应分支，并在 `engine.test.ts` 加用例——
  ref 路径那个 bug 就是这样被抓到的。
- 改图标：`pnpm icons`（脚本零依赖，产物需一起提交）。
- 不要给 Workbox 加 API 的 runtimeCaching，理由见本文 D-10。
