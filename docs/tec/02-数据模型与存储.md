# 02 · 数据模型与存储

## 1. 数据仓库文件布局

数据仓库：`salenju/my-collector-data`（**Private**，与前端仓库完全独立）。

```
my-collector-data/
├── README.md                       # 说明"这是满天星的数据仓库，勿手改结构"
└── data/
    ├── meta.json                   # 索引：schema 版本、分片清单、同步元信息
    ├── tags.json                   # 标签定义（全量，单文件）
    └── items/
        ├── 2026-09.json            # 按 createdAt 月份分片
        ├── 2026-10.json
        └── ...
```

### 1.1 为什么按月分片（D12）

| 方案 | 优点 | 缺点 |
| --- | --- | --- |
| 单文件 `items.json` | 读取只需 1 请求 | 每次写入整文件，diff 噪声大，>1MB 触发 Contents API base64 限制（约 2000 条），未来必须迁移 |
| **按月分片（采用）** | 每次 commit 只改一个小文件，diff 干净；冲突面小；天然突破 2000 条上限，多年不用迁移 | 冷启动需 N 次请求（N = 使用月数） |

结论：**从 v1 就分片**，避免将来做数据迁移。分片键固定为 `createdAt` 的 `YYYY-MM`，
即**条目永久留在创建时的分片里**，编辑不会导致条目跨分片移动（避免"删除旧文件 + 新增新文件"的复杂写入）。

冷启动 N 次请求的成本由三点抵消：
1. **Git Trees API 一次拿到全仓库文件 sha**（1 个请求），未变更的文件**根本不发请求**；
2. 并发拉取变更的分片（并发上限 6）；
3. 带 `If-None-Match` 的条件请求作为兜底，未变更返回 304 且**不计入限流额度**。

个人使用 3 年 = 36 个分片，但每日实际变化的通常只有 1 个，日常增量同步 ≈ 2~3 个请求。
（实现细节与原因见 [09-实现记录.md](./09-实现记录.md) D-01。）

## 2. 数据模型

### 2.1 Item（条目）

```ts
type ItemType = 'link' | 'note';
type ItemSource = 'web' | 'bookmarklet' | 'extension' | 'share' | 'import';

interface Item {
  /** nanoid(10)，全局唯一，客户端生成（无服务端自增 ID） */
  id: string;
  type: ItemType;

  /** 链接标题 / 笔记标题；笔记允许为空（空标题在列表用内容首行代替展示） */
  title: string;

  /** 仅 type=link 存在。已归一化（去除 utm_* 等追踪参数，见 §2.5） */
  url?: string;

  /** 用户自己写的正文：收藏理由、笔记内容、摘录 */
  content: string;

  /** 抓取到的网页摘要（og:description），抓取失败为空字符串 */
  excerpt?: string;

  /** 站点图标地址（存 URL 不存 base64，见 §2.6） */
  favicon?: string;

  /** 标签 ID 数组（引用 tags.json） */
  tagIds: string[];

  /** 记录来源，用于统计与「一键收藏」排查 */
  source: ItemSource;

  /** ISO 8601 UTC，创建时间。同时决定所属分片 */
  createdAt: string;

  /** ISO 8601 UTC，最后修改时间。冲突合并的判定依据 */
  updatedAt: string;

  /** 归档：默认不入列表主视图，但完整保留 */
  archived: boolean;

  /** 软删除墓碑：非 null 表示已删除，仅回收站可见（见 §2.4） */
  deletedAt: string | null;

  /** 预留扩展位：阅读状态、评分、抓取快照等 */
  metadata: Record<string, unknown>;
}
```

**字段设计要点**

| 字段 | 为什么这样设计 |
| --- | --- |
| `id` 客户端生成 | 离线也能创建，不依赖服务端分配；nanoid(10) 碰撞概率可忽略 |
| `createdAt` 决定分片 | 分片路由是纯函数 `shardOf(item) = createdAt.slice(0,7)`，无状态 |
| `title` 可空 | 碎片笔记常常没标题，强制标题会打断记录流 |
| `excerpt` 与 `content` 分离 | 抓来的内容不能覆盖用户手写内容，二者语义不同 |
| `tagIds` 存 ID 不存名字 | 改标签名时不必批量改写所有条目 |
| `deletedAt` 而非直接移除 | 多端同步必须能传播"删除"这个动作，否则会把本地已删条目重新拉回来 |

### 2.2 Tag（标签）

```ts
type TagColor = 'blue' | 'amber' | 'violet' | 'emerald' | 'rose' | 'cyan'
              | 'orange' | 'teal' | 'indigo' | 'pink' | 'lime' | 'slate';

interface Tag {
  /** 'tag_' + nanoid(8) */
  id: string;
  /** 展示名（大小写不敏感去重） */
  name: string;
  /** 调色板键名；UI 层映射为完整 Tailwind 类名（不能动态拼接类名） */
  color: TagColor;
  /** 预留层级（v1 恒为 null，升级为树形无需改数据） */
  parentId: string | null;
  createdAt: string;
  /** 与 Item 一样参与 LWW 合并；改名/改色都需靠它裁决冲突 */
  updatedAt: string;
  /** 软删除墓碑：非 null 表示已删除，用于正确传播"删除标签" */
  deletedAt: string | null;
}
```

> **实现期修正（见 [09-实现记录.md](./09-实现记录.md) D-04）**：原 schema 只有 `createdAt`，
> 无法表达「两台设备同时改标签」以及「删除标签」，会出现"另一端已删除的标签被本机复活"。
> 现在标签与条目共用同一套 LWW + 墓碑合并逻辑。

**v1 标签规则**

- 扁平列表，按 `name` 排序展示，选中数倒序（常用靠前）。
- 输入时自动补全；输入不存在的名字 → 回车即时创建新标签。
- 标签名去重规则：`trim()` + 大小写不敏感比较；重名直接复用已有标签。
- 颜色：新建时从预设调色板按 `hash(name) % palette.length` 自动分配，可在标签管理页改。
- 删除标签：因为是引用式（`tagIds`），删除标签需同时从所有条目的 `tagIds` 中摘除，
  这是一次多文件写入 → 走原子提交（见 03 文档 §4）。删除前二次确认并提示影响的条目数。

### 2.3 Meta（全局元信息）

> **实现期修正（见 [09-实现记录.md](./09-实现记录.md) D-01）**：原设计把分片清单与 `blobSha` 放进
> `meta.json` 用于跳过未变更文件，但 `meta.json` 与分片文件属于**同一次提交**，其内容无法包含本次提交
> 之后各分片的新 sha，形成循环依赖。现改为用 **Git Trees API** 一次请求拿到全仓库文件 sha
> （比原方案更省请求），`meta.json` 只保留不会自指的字段。

```json
{
  "schemaVersion": 1,
  "createdAt": "2026-09-27T11:00:00Z",
  "tokenExpiresAt": "2026-12-26",
  "deviceNames": { "device_7f3a91": "MacBook Chrome" }
}
```

| 字段 | 用途 |
| --- | --- |
| `schemaVersion` | 未来数据迁移的开关；应用读到更高版本时进入只读模式并提示升级 |
| `createdAt` | 数据仓库创建时间（用于在 UI 上展示"始于何时"） |
| `tokenExpiresAt` | 用户在设置页填写 PAT 时一并记录，所有设备共享到期提醒（≤7 天告警） |
| `deviceNames` | 设备 ID → 可读名，便于冲突追溯；每次推送 meta 时更新当前设备名 |

**不在 meta.json 中的信息**（避免自指与无意义提交）：

| 信息 | 现在的存放位置 |
| --- | --- |
| 分片清单、各文件 sha | 每次同步由 `GET /git/trees/{branch}?recursive=1` 现场获得 |
| `lastSyncAt`、`lastDeviceId` | **设备本地**状态（IndexedDB settings），因为它天然是"每台设备各自的时间" |
| 文件的 ETag | 设备本地 `fileCache` 表 |
| HEAD 提交 / 根 tree sha | 设备本地 `RemoteSnapshot`（用于 CAS 预检与 `base_tree`） |

**收益**：`meta.json` 不再需要在每次推送时重写，只在设备名变化或初始化时提交，提交历史更干净；
同时冷启动的请求数从「1 + N 个分片」降为「1 次 Trees + 仅变更的分片」。

### 2.4 归档与软删除语义

| 状态 | 字段 | 列表主视图 | 搜索 | 说明 |
| --- | --- | --- | --- | --- |
| 正常 | `archived=false, deletedAt=null` | 显示 | 命中 | 默认 |
| 归档 | `archived=true, deletedAt=null` | 不显示（"归档"视图可见） | 命中 | 处理完了但想留着 |
| 软删除 | `deletedAt != null` | 不显示 | 不命中 | 墓碑，回收站可见（回收站 UI 排 a2） |

**墓碑的清理**：墓碑会永久留在数据里。引入 `purge` 策略：把 `deletedAt` 早于 90 天的条目
**从文件中物理移除**（该变更会作为一次 commit，Git 历史里仍可找回）。
v1 默认关闭自动清理（保守），只在设置里提供「立即清理 N 条墓碑」的显式按钮（`purgeTombstones(0)`）。

> 实现说明：清理**不是**在 pull 时顺手做，而是走一条独立的待推送单元
> ——`outbox` 里 `entity='shard'`（`entityId=YYYY-MM`，`purgedIds` 记录被移除的 id），
> 由 push 把该月分片整片重写；pull 侧再用 `purgedIds` 拦住"远端墓碑复活"。
> 细节与取舍见 04 文档 §4.3。

### 2.5 URL 归一化规则

记录链接时做最小归一化，便于去重与展示：

1. 去 fragment（`#...`）；
2. 去追踪参数：`utm_*`、`fbclid`、`gclid`、`spm`、`scm`、`ref`、`from`；
3. 保留其余查询参数（可能承载真实内容，如 `?id=123`）；
4. 协议只允许 `http` / `https`（其余如 `javascript:`、`file:` 一律拒绝，见 08 文档 §3）；
5. 展示时用 `new URL(url).host` 作为域名标签。

提供「重复链接检测」：保存时若已存在同 `url`（归一化后相同）的**未删除**条目，
提示"已收藏过（时间）"，给出「仍然新增 / 打开原条目 / 取消」三个选项，不强制阻止。

### 2.6 favicon 与图片策略

- **只存 URL，不存 base64**：避免把二进制塞进 JSON（会让文件体积不可控、diff 不可读）。
- 优先 `{origin}/favicon.ico`；加载失败时前端降级为「域名首字母 + 按域名 hash 生成的背景色」色块。
- **默认不使用**第三方 favicon 服务（如 Google s2），因为它会把域名泄露给第三方；需用户显式开启。

## 3. 文件格式与序列化约定

| 约定 | 内容 | 原因 |
| --- | --- | --- |
| 缩进 | `JSON.stringify(data, null, 2)` | Git diff 可读、可 review |
| 换行 | 文件末尾保留一个 `\n` | 避免 diff 出现 `\ No newline at end of file` |
| key 顺序 | 保持对象字面量声明顺序（不排序） | 稳定输出，减少无意义 diff |
| 编码 | UTF-8，提交时 `btoa(unescape(encodeURIComponent(str)))` | 直接 `btoa` 遇中文会抛 `InvalidCharacterError` |
| 空值 | 统一用 `null`（数组为空用 `[]`，字符串为空用 `""`） | 避免 `undefined` 被 `JSON.stringify` 丢弃导致结构不一致 |
| 时间 | 全部 ISO 8601 UTC（`Z` 结尾） | 多设备时区无关，字符串可比较排序 |

分片文件的内部结构：

```json
{
  "version": 1,
  "month": "2026-09",
  "items": [ /* Item[] */ ]
}
```

## 4. 数据校验与容错

### 4.1 读取侧（防坏数据污染本地）

pull 后对每个文件执行三层校验，**任何一层失败都不写入本地索引**：

1. **结构校验**：`version` / `month` / `items` 字段存在且类型正确。
2. **条目守卫**：手写 `isItem(v)` 逐字段校验（`id` 非空字符串、`type` 在枚举内、
   `tagIds` 是字符串数组、`createdAt` 可被 `Date.parse`、`deletedAt` 为 `null|string`）。
3. **归一化修复**：对可无损修复的问题就地修复并记警告（例：`tagIds` 中引用了不存在的标签 → 保留但 UI 标记为"未知标签"；
   `title` 缺失 → 置 `""`）。不可修复的条目**跳过**并在同步状态栏显示"跳过 N 条异常数据"。

> 设计原则：**宁可少显示一条，也不让一条坏数据破坏整个本地缓存**。

### 4.2 写入侧（防自造坏数据）

本应用是唯一写入者，写入前对 Item 做同一套守卫校验；
写入后立刻做一次本地"读回校验"（parse 一遍生成的 JSON 字符串），失败则中止提交并报错。

### 4.3 Schema 演进

- `data/meta.json.schemaVersion` 是全局开关。
- 应用代码内置 `CURRENT_SCHEMA_VERSION = 1`。
  - 远端 `==` 本地：正常。
  - 远端 `>` 本地：**只读模式**，顶部提示"数据由更新版本的应用写入，请升级"，避免旧版覆盖新结构。
  - 远端 `<` 本地：进入迁移流程（v1 无迁移逻辑，仅预留 `migrations[]` 空表）。
- 单文件内的 `version` 字段用于文件级演进（例如分片结构从"按月"改为"按标签"）。

## 5. 容量边界与演进触发条件

| 指标 | 当前设计边界 | 触发动作 |
| --- | --- | --- |
| 单分片条目数 | 软上限 1000 条（≈500KB） | 单月超 1000 条（不太可能）→ 月份分片二次切分为 `YYYY-MM-1.json` |
| 分片总数 | 数百个无压力 | > 200 个（约 16 年）→ 改为按年分片 |
| 单条 item 大小 | 建议 < 8KB | 超限时提示"内容过长，建议拆分为笔记" |
| tags.json | 数千标签无压力 | > 2000 个 → 改为 `tags/` 分片 |
| 冷启动请求数 | 1 次 Trees + 变更分片数 | 引入 `data/index.json` 做二级索引（仅在实测慢时再做） |
| 全文检索 | 内存过滤，无索引 | 条目 > 5000 且实测卡顿 → 引入 Fuse.js / 拼音索引（D8 的 a2 计划） |

## 6. 数据仓库初始化内容

> **仓库不需要手工准备**：可以是完全空的，也可以只包含建仓时自动生成的 `README.md`
> （GitHub 新建仓库默认会勾选 "Add a README"）。
> 初始化判据是 **`data/meta.json` 是否存在**，而不是「仓库是否为空」——
> 已有提交时会在既有 tree 上增量提交（`base_tree` = 当前 HEAD 的 tree），原有文件会被保留。
> 见 [09-实现记录.md](./09-实现记录.md) D-09。

应用「初始化数据仓库」按钮会创建以下内容（一次原子提交完成，见 03 文档 §4.4）：

**`data/meta.json`**
```json
{
  "schemaVersion": 1,
  "createdAt": "2026-09-27T11:00:00.000Z",
  "tokenExpiresAt": null,
  "deviceNames": { "device_7f3a91": "MacBook Chrome" }
}
```

**`data/tags.json`**
```json
{
  "version": 1,
  "tags": [
    { "id": "tag_tech",  "name": "技术", "color": "blue",   "parentId": null },
    { "id": "tag_read",  "name": "待读", "color": "amber",  "parentId": null },
    { "id": "tag_idea",  "name": "想法", "color": "violet", "parentId": null }
  ]
}
```
> 预置三个标签是为了让首次进入的界面不是空的，用户可随意删改。

**`data/items/YYYY-MM.json`**（当前月，`YYYY-MM` 取执行时 UTC 月份）
```json
{ "version": 1, "month": "2026-09", "items": [] }
```

**`README.md`**
```markdown
# 满天星 · 数据仓库

此仓库是「满天星」收藏工具的数据存储（GitHub 即数据库）。
- 结构请勿手工修改，所有变更由应用通过 Contents / Git Data API 提交。
- 每次写入都是一次 commit，可通过 git log / git diff 追溯与回滚。
```
