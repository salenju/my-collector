# 04 · 同步引擎与冲突处理

这是整个方案最需要打磨的部分：**离线优先 + 多设备一致性**。

## 1. 本地存储（Dexie / IndexedDB，D6）

```ts
// core/src/store/schema.ts
db.version(1).stores({
  items:      'id, createdAt, updatedAt, type, archived, deletedAt, *tagIds',
  tags:       'id, name, updatedAt, deletedAt',         // parentId 已预留（v1 恒为 null），不建索引
  outbox:     '++seq, entity, entityId, at',            // 待推送变更队列（按 seq 保序）
  fileCache:  'path',                                   // { path, sha, etag, size, updatedAt }
  settings:   'key',                                    // github / device / ui / sync / mergePolicy
  meta:       'key',                                    // 远端 meta.json 的本地镜像 + 远端快照
  drafts:     'key',                                    // 未提交的表单草稿（防误关页面丢内容）
  metadataCache: 'url, at',                             // 元信息抓取结果缓存（04 文档之外的补充）
  assets:     'key, sha, status, at, lastAccessAt',     // v2：附件图片字节（待上传 + 本地缓存）
});
```

| 表 | 作用 | 关键点 |
| --- | --- | --- |
| `items` | 本地全量条目快照 | 是 UI 的唯一数据源（**UI 永不直接读 GitHub**） |
| `tags` | 本地标签表 | 与 items 一同参与合并（LWW + 墓碑）；`parentId` 已预留但 v1 恒为 `null` |
| `outbox` | 未推送的变更队列 | **核心表**：应用"先本地后远端"的落地处。`entity` 取 `item` / `tag` / `meta` / `shard`（`shard` 表示「该分片整体重写」，见 §4.3）/ `asset`（`entityId` = 图片内容 id，见 10 文档 §6.3） |
| `fileCache` | 远端文件 `sha`/`etag` 镜像 | 支持 304 条件请求与"跳过未变更文件" |
| `settings` | Token、仓库配置、设备 ID、UI 偏好、`mergePolicy` | 设备 ID 首次运行生成并持久化 |
| `meta` | 远端 meta 镜像 + 远端快照 | `pull` 时的更新依据（schemaVersion、commitSha/treeSha/files） |
| `drafts` | 表单草稿 | 用户在 /new 输入到一半关掉页面也不丢 |
| `metadataCache` | 元信息抓取缓存 | 按 URL 缓存 title/excerpt，避免重复抓取 |
| `assets` | 附件图片字节（v2） | **一张表两个角色**：`status='pending'` 是待上传队列（带字节），`'uploaded'` 是已下载缓存。LRU 淘汰必须跳过 `pending`——那是尚未上传的用户数据 |

**设备 ID**：首次运行 `nanoid(8)` 生成，存 `settings.device`。
建议同时让用户设置可读名（"MacBook Chrome"），写入远端 `meta.deviceNames`，便于冲突追溯。

## 2. 同步状态机

```
            ┌──────────────────────────────────────────────────┐
            │                                                  │
            ▼                                                  │
      ┌──────────┐   pull成功且outbox为空   ┌──────────┐        │
      │  synced  │◄────────────────────────│ syncing  │        │
      └────┬─────┘                         └────┬─────┘        │
           │ 本地写入 / 手动刷新 / 窗口聚焦         │              │
           ▼                                    │ 422 冲突      │
      ┌──────────┐   网络失败                  │              │
      │ pending  │──────────────────────►┌─────▼──────┐        │
      │ (有outbox)│                      │ merging    │        │
      └────┬─────┘                      └─────┬──────┘        │
           │                                  │ 合并后重试      │
           │                                  └───────────────┘
           │ 断网                                  │ 重试 3 次仍失败
           ▼                                      ▼
      ┌──────────┐                          ┌────────────┐
      │ offline  │  网络恢复(online 事件)     │  conflict  │
      └────┬─────┘──────────────────────────►（需人工介入）│
           │                                 └────────────┘
           ▼
      ┌──────────┐
      │ backoff  │  限流/5xx → 按 retryAfter 倒计时
      └──────────┘
```

状态对用户的呈现（顶栏同步指示器）：

| 状态 | 图标 | 文案 | 用户可做的操作 |
| --- | --- | --- | --- |
| `synced` | ✅ | 已同步 · 2 分钟前 | 手动刷新 |
| `pending` | ⏳ | 有 N 条待同步 | 立即同步 |
| `syncing` | 🔄 | 同步中… | — |
| `offline` | 📴 | 离线模式，本地记录正常 | 重试 |
| `backoff` | ⏱ | 触发限流，X 分钟后重试 | 立即重试 |
| `conflict` | ⚠️ | N 条冲突待处理 | 查看冲突 / 导出备份 |
| `auth-error` | 🔑 | Token 失效 | 去设置 |

## 3. 读流程 `pull()`

```
pull()
 ├─ 未配置 Token → 跳过（不报错）
 ├─ Web Locks 拿锁（'my-collector:sync'），拿不到说明别的标签页正在同步 → 跳过
 ├─ GET 分支 ref + commit（空仓库返回 null → 提示需要初始化）
 ├─ GET /git/trees/{branch}?recursive=1 → 一次拿到全仓库文件 sha + 根 tree sha
 ├─ 读 data/meta.json（sha 与本地不同才读）→ 校验 schemaVersion（> 本地 → 只读模式并中止）
 ├─ 计算变更文件集：
 │    staleShards = 分片文件.filter(远端 sha !== fileCache.sha(path))
 │    tagsStale   = tags.json 的远端 sha !== fileCache.sha('data/tags.json')
 ├─ 并发拉取（限并发 6，每个带 If-None-Match）
 │    ├─ 200 → 解码 base64（注意 UTF-8）→ JSON.parse → 校验
 │    └─ 304 → 读本地缓存内容
 ├─ 校验/归一化（见 02 文档 §4.1）：坏条目跳过并计数
 ├─ 与本地 + outbox 合并（§5）
 ├─ 事务写入：items(受影响) / tags / meta / fileCache
 └─ 刷新内存快照 → 通知 UI（Pinia 订阅）
```

**关键细节**
- base64 → UTF-8 解码：`decodeURIComponent(escape(atob(content)))` 或 `TextDecoder`，**不能直接 `atob`**（中文乱码）。
- 304 的响应没有 `content` 也没有新 `sha`，必须使用本地缓存内容；因此 `fileCache` 里要同时存内容吗？
  **不存**——`items` 表本身就是"缓存内容"，304 时无需重建。`fileCache` 只存 `sha/etag` 元信息。
- 分片拉取失败（单文件 5xx）：整体 pull 标记失败，**不写入任何远端数据**，保持上一次一致状态（避免出现"只有一半分片是新的"）。

## 4. 写流程

### 4.1 本地写入（同步、立即成功）

```ts
async function upsertItem(input: ItemInput): Promise<void> {
  await db.transaction('rw', db.items, db.outbox, async () => {
    const now = new Date().toISOString();
    const existing = input.id ? await db.items.get(input.id) : undefined;
    const item: Item = {
      ...defaults,
      ...existing,
      ...input,
      updatedAt: now,
      createdAt: existing?.createdAt ?? input.createdAt ?? now,
    };
    if (!isItem(item)) throw new ValidationError(item);   // 写入前守卫
    await db.items.put(item);
    await db.outbox.add({ entity: 'item', entityId: item.id, action: 'upsert', at: now });
  });
  snapshot.refresh();          // 内存快照 + UI 乐观更新
  schedulePush();              // 2s debounce（最长 5s 强制）
}
```

**要点**
- 一个 Dexie 事务里同时写业务数据和 outbox，保证"改了但没入队"不可能发生。
- **附件图片（v2）**：`stage()` 先压缩并把图片字节写进 `assets` 表（`pending`），
  再由同一个事务把 `entity='asset'` 入队。图片字节与条目 JSON 在同一次原子提交里推上去，
  因此不会出现"条目引用了图片、但图片没进队列/没上传"（见 10 文档 §6.3）。
- `outbox` 按 `entityId` **压缩**：同一实体的多次修改只保留最后一次（`action='upsert'` 覆盖旧的 upsert；
  `create` + `delete` 若都还没推送 → 两者直接抵消、都丢弃，省一次无意义提交）。

### 4.2 推送 `push()`

```ts
async function push(): Promise<void> {
  const ops = await drainOutboxSnapshot();          // 取当前队列快照（不删）
  const affected = planAffectedFiles(ops);          // → ['data/items/2026-09.json', 'data/tags.json', 'data/meta.json']

  // 1. 基于"本地最新快照"渲染每个受影响文件的完整内容
  //    分片：把该月**全部**条目（含墓碑）按 createdAt 排序输出。
  //    墓碑必须写进文件——删除正是靠它传播给其他设备（"文件里没有 = 没删过"）。
  const files = await renderFiles(affected);

  // 2. 原子提交（见 03 文档 §4.2）
  const result = await gitData.commitAtomic({
    files,
    message: buildMessage(ops, deviceId),
    expectedHeadSha: lastKnownHeadSha,              // CAS
    baseTreeSha: lastKnownTreeSha,
  });

  // 3. 成功 → 清队列、更新缓存
  await db.transaction('rw', db.outbox, db.fileCache, db.meta, async () => {
    await db.outbox.bulkDelete(ops.map(o => o.seq));
    updateFileCache(result);                        // 写入新的 blobSha（分片）
    await db.meta.put({ key: 'remote', ...result.metaMirror });
  });
  setState('synced');
}
```

**为什么要 `expectedHeadSha` 而不是只依赖 `base_tree`**：
`base_tree` 决定"保留哪些未变更文件"，而 `expectedHeadSha` 决定"父提交是谁"，
后者才是并发检测点（父提交不是当前 HEAD → 非快进 → 422）。两者都需要，语义不同。

**提交失败的处理**

| 失败类型 | 处理 |
| --- | --- |
| `conflict` (422) | 立即 `pull()` → 合并 → 重放 outbox → 重试（最多 3 次；**中间不 sleep**——合并本身就是"把本地操作重新排一次队"，等待只会让用户更晚看到结果）→ 仍失败转 `conflict` 状态 |
| `network` | 转 `offline`，监听 `online` 事件 + 退避阶梯重试 |
| `rate-limit` | 转 `backoff`，按 `x-ratelimit-reset` 精确等待 |
| `server` (5xx) | 退避重试最多 5 次 → 转 `conflict`（提示用户稍后重试，本地数据不丢） |
| `auth` / `forbidden` | 停止自动重试，转 `auth-error`，引导去设置页 |
| 校验失败（本地渲染出错） | 中止提交，报 bug 级错误，**不删 outbox**，提示导出备份 |

### 4.3 清理墓碑（物理移除，必须整片重写）

墓碑（`deletedAt != null`）会永久留在数据里：它要一直在文件中，其他设备才知道"这条被删过"。
`purge` 是唯一的物理移除手段——设置页「清理墓碑」按钮（`purgeTombstones(0)`）或 `purgeItem(id)`。

**难点**：条目行被物理删掉之后，push 时无法再由 `id` 反推它属于哪个月份，普通的按实体入队
（`outbox.entity='item'`）会渲染不出任何文件——这正是"清理墓碑看起来生效、实际没写回远端"的成因。
因此引入一种新的待推送单元：

```ts
// entity='shard'、entityId='YYYY-MM'：该分片文件需要整体重写
// purgedIds：本次物理移除的条目 id（与已有记录取并集，防止同月多次清理互相覆盖）
await db.outbox.add({
  entity: 'shard', entityId: month, action: 'upsert', at: now, purgedIds: [id],
});
```

- **推送**：`renderAffectedFiles()` 把 `shard` 操作还原成"重写该月分片"，于是文件里不再有这条墓碑，
  该变更就是一次 commit（Git 历史里仍可找回）。
- **拉取**：如果推送之前先发生了一次 pull，远端文件里**还带着**这条墓碑，照常合并就会把它拉回本地，
  让清理白做（下一次 push 又把它写回去）。因此 `pull` 会把 outbox 里的 `purgedIds` 汇成集合传给
  `merge()`，命中时**不采纳远端那条**，并在冲突日志里记一条 `reason='purged'` 便于追溯（§5.2 #15）。

> 取舍：只拦"被清理的那个 id"，而不是整片忽略远端——后者会让另一台设备在该月的新记录
> 在下次整片重写时被静默丢掉。

## 5. 冲突合并（merge.ts，纯函数、可单测）

### 5.1 合并粒度与规则

**按条目的 `id` 粒度做 LWW（Last-Write-Wins）**，`updatedAt` 为裁决依据。

```
merge(base=本地, remote=远端, outbox) -> 合并结果
  1. 取两侧条目并集（按 id 建 map）
  2. 对每个 id：
     a) 仅一侧存在 → 保留该侧；**例外**：远端有、本地没有，且该 id 在本地刚被物理清理
        （§4.3 的 purgedIds）→ 不采纳（否则清理会被下一次拉取撤销）
     b) 两侧都存在：
        - updatedAt 相同 → 内容视为一致，取任一侧（校验一致性，不一致则记警告）
        - updatedAt 不同 → 取较大者
        - 一侧是墓碑（deletedAt != null）→ 按 `mergePolicy` 裁决，见 §5.2 #8：
          `delete-wins`（默认）不看时间戳，只要一侧是墓碑就删除生效；
          `edit-wins` 不特判墓碑，仍按 updatedAt（删除可能被更晚的编辑覆盖回来）
  3. 最后重放 outbox（本地未推送的变更优先级最高，因为它是"用户刚刚的操作"）
     - outbox 中的 upsert：若其 updatedAt > 合并结果 → 覆盖；否则丢弃该 op（服务端已更新，本地操作已过期）
     - outbox 中的 delete：直接置墓碑并更新 updatedAt
  4. 结果去重、按 createdAt 排序、按分片归类
```

### 5.2 冲突矩阵（必须单测覆盖）

| # | 本地 | 远端 | 期望结果 | 说明 |
| --- | --- | --- | --- | --- |
| 1 | 新增 A | 无 A | 保留 A | 只有本地有 |
| 2 | 无 B | 新增 B | 保留 B | 只有远端有 |
| 3 | A(t1) | A(t1) 同内容 | 无冲突 | 常态 |
| 4 | A(t2) 改了标题 | A(t1) | 取本地 | LWW：本地更新 |
| 5 | A(t1) | A(t3) 改了标签 | 取远端 | LWW：远端更新 |
| 6 | A 删除(t2) | A(t1) | 删除生效 | 删除按时间裁决 |
| 7 | A(t1) | A 删除(t2) | 删除生效 | 远端删除更新 |
| 8 | A 编辑(t2) | A 删除(t3) | 删除生效 | 后发生的删除赢（可在设置中改为"编辑优先"） |
| 9 | outbox: A(t5) | A(t4) | 取 outbox 的 A(t5) | 本地刚点的操作不丢 |
| 10 | outbox: A(t3) | A(t4) | 取远端 A(t4)，丢弃 op | 本地操作已被远端覆盖 |
| 11 | outbox: 新增 A | 已有 A | 取 outbox 版本 | 同 id 撞车概率可忽略（nanoid） |
| 12 | A 归档(t2) | A(t1) | 归档生效 | `archived` 也是普通字段 |
| 13 | 本地 A 正常，远端 A 的 `tagIds` 引用了本地不存在的标签 | 标签缺失 | 保留 tagId 但 UI 标"未知标签" | 不因标签缺失丢数据 |
| 14 | 同 id 两侧 `updatedAt` 相同但内容不同 | 数据被外部手改过 | 取远端 + 记警告；**但本地该条有未推送操作时取本地**，不吞掉用户刚点的操作 | 上报"检测到手工修改冲突" |
| 15 | 本地已物理清理（墓碑被移除） | 远端仍带着该墓碑 | 不采纳远端，记 `reason='purged'` | 清理墓碑不被下一次拉取撤销（§4.3） |

> 规则 #8 是唯一的策略性选择：**删除优先于编辑**。理由：误删可回滚（Git 历史 + 墓碑），
> 而"删了又被编辑拉回来"会让用户困惑。此策略在设置页可切换（`mergePolicy: 'delete-wins' | 'edit-wins'`）。

> **附件图片不新增任何冲突条目（v2）**：图片是**内容寻址且永不修改**的（文件名即其 sha256），
> 两端上传同一张图必然落到同一个路径、产生相同的内容，因此不存在图片级冲突。
> `item.assets` 只是普通数组字段，`updatedAt` 的 LWW 已经覆盖"两端同时增删图片"的情况；
> 图片的"删除"就是数组变短，不需要墓碑（见 10 文档 §7.2、§8）。

### 5.3 合并后的报告

合并涉及真正冲突（同一 id 两侧都改）时，记录一条 `conflictLog`：
```ts
interface ConflictEntry {
  itemId: string;
  keptSource: 'local' | 'remote';
  localUpdatedAt: string;
  remoteUpdatedAt: string;
  at: string;
}
```
在同步状态面板展示"N 条冲突已自动解决"，可展开查看明细；**所有被覆盖的内容都还在 Git 历史里**，
面板提供"查看这条记录的 Git 历史？"链接（指向 `https://github.com/salenju/my-collector-data/commits/main/{path}`）。

### 5.4 无法自动解决的冲突（人工介入）

v1 认为以下情况需要人工：合并重试 3 次仍失败（通常是网络或极端并发）。
此时：
1. 状态置 `conflict`，顶栏红色横幅；
2. 提供「导出本地数据为 JSON」按钮（一键备份，不怕丢）；
3. 提供「使用远端覆盖本地」与「重试」两个动作；
4. 不提供"强制推送"（会丢数据）。

## 6. 触发时机与调度

| 触发 | pull | push |
| --- | --- | --- |
| 应用启动 | ✅ | 若 outbox 非空 ✅ |
| 窗口/标签页重新获得焦点（间隔 ≥ 60s） | ✅ | ✅ |
| 本地写入后 | — | ✅（debounce 2s，最长 5s） |
| 手动点同步 | ✅ | ✅ |
| `online` 事件 | ✅ | ✅ |
| 定时（仅当有 outbox 时） | — | ✅ 退避重试：2s → 5s → 15s → 60s → 300s 封顶 |
| `visibilitychange` → hidden | — | ✅ 立即 flush（避免用户在移动端切走后数据没发出去） |

**不做**：定时轮询远端（费额度且个人场景无必要）、WebSocket、任何实时推送。

## 7. 多标签页与锁降级

```ts
// core/src/sync/lock.ts
const locks = navigator.locks;
if (locks) {
  // 同源跨标签页互斥；ifAvailable: true 让"另一个标签页正在同步"变成
  // 正常跳过而非排队等待（用户无感）
  return locks.request('my-collector:sync', { ifAvailable: true }, async lock => {
    if (!lock) return null;
    return fn();
  });
}
// 降级：进程内 Set 互斥（同一页面内的 pull/push 不重叠）
return acquireInProcessLock('my-collector:sync');
```

**降级后跨标签页并发怎么保证安全**：不做 Dexie lease（原设计），而是交给 GitHub 的 CAS
（`updateRef` 用 `force:false`，分支被推进即 422）+ 自动合并兜底——最多多一次往返，不会丢数据。
理由：lease 本身要处理续约、过期、时钟偏差三种失败模式，代价高于它挡住的这一次多余提交。
