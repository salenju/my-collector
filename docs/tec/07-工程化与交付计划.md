# 07 · 工程化与交付计划

## 1. Monorepo 与工程配置

### 1.1 根配置

```yaml
# pnpm-workspace.yaml
packages:
  - 'packages/*'
```

```jsonc
// package.json（根）
{
  "name": "my-collector",
  "private": true,
  "packageManager": "pnpm@9",
  "engines": { "node": ">=20" },
  "scripts": {
    "dev":        "pnpm -F @my-collector/web dev",
    "dev:ext":    "pnpm -F @my-collector/extension dev",
    "build":      "pnpm -F @my-collector/core build && pnpm -F @my-collector/web build",
    "build:ext":  "pnpm -F @my-collector/extension build",
    "preview":    "pnpm -F @my-collector/web preview",
    "test":       "vitest run",
    "test:watch": "vitest",
    "typecheck":  "pnpm -r typecheck",
    "smoke":      "node scripts/smoke.mjs",
    "icons":      "node scripts/gen-icons.mjs"
  }
}
```

> **实现状态**：以上脚本已全部可用（`lint` / `format` 尚未落地，见 09 文档 §六）。
> `smoke` 需要本机 Chrome：先后台起 `pnpm preview`，再执行 `pnpm smoke`。

### 1.2 为什么用 monorepo（而非单 Vite 项目）

| 理由 | 说明 |
| --- | --- |
| 消除双实现漂移 | 扩展与 Web 共享 `core` 的合并/分片/提交逻辑。若各写一份，一年后必然行为不一致（最典型的坑：删除语义不同导致数据互相"复活"） |
| 数据模型单一真源 | `Item`/`Tag` 类型只定义一次，改字段只改一处 |
| 测试一次覆盖两端 | `merge.ts` 的单测同时保障 Web 与扩展 |
| 成本可控 | pnpm workspace 只需一个配置文件；`core` 用 `tsc` 出 ESM 即可，无需复杂构建链路 |

**如果后续觉得太重**：可退化为单包 + `src/core/` 目录（用路径别名共享），扩展单独目录引用同一源码。
但建议先用 monorepo，因为扩展是已确认要做的功能。

### 1.3 代码质量约束

| 工具 | 规则要点 |
| --- | --- |
| TypeScript | `strict: true`、`noUncheckedIndexedAccess: true`、`exactOptionalPropertyTypes` |
| ESLint | `eslint-plugin-vue`（flat config）、禁止 `v-html`（自定义规则/`vue/no-v-html` 置 error）、禁止 `any` |
| Prettier | `singleQuote: true`、`printWidth: 100`、`semi: true` |
| vue-tsc | CI 中必须 0 error |
| 提交规范 | Conventional Commits（`feat/fix/docs/chore/refactor`），便于看 `git log` 追溯 |

### 1.4 环境变量

| 变量 | 用途 | 默认 |
| --- | --- | --- |
| `VITE_APP_TITLE` | 应用名 | 满天星 |
| `VITE_DEFAULT_REPO_OWNER` | 设置页预填 | salenju |
| `VITE_DEFAULT_REPO_NAME` | 设置页预填 | my-collector-data |
| `VITE_METADATA_PROVIDER` | 抓取提供方 | jina |
| `VITE_METADATA_CUSTOM_URL` | 自建代理地址 | 空 |

> **不设置任何密钥类环境变量**。前端产物是公开的，凡是"密钥"都必须由用户在运行时输入。

## 2. 构建

### 2.1 Web（Vite）

```ts
// packages/web/vite.config.ts
export default defineConfig(({ mode }) => ({
  base: '/my-collector/',                       // ① 子路径
  plugins: [
    vue(),
    VitePWA({
      registerType: 'prompt',                    // ② 不强制刷新，避免丢表单
      includeAssets: ['favicon.ico', 'apple-touch-icon.png'],
      manifest: manifest,                        // 见 06 文档 §3.1
      workbox: {
      globPatterns: ['**/*.{js,css,html,ico,png,svg,woff2}'],
      navigateFallback: '/my-collector/index.html',
      // 刻意不缓存 GitHub API 响应：否则离线时会用「陈旧但看起来成功」的远端数据
      // 参与冲突合并。理由见 09-实现记录.md D-10。
      runtimeCaching: [],
      cleanupOutdatedCaches: true,
      },
    }),
    copyIndexTo404(),                            // ③ 生成 404.html 兜底
  ],
  build: { target: 'es2020', sourcemap: mode !== 'production', rollupOptions: { output: { manualChunks: { vendor: ['vue','vue-router','pinia'], octokit: ['@octokit/core'] } } } },
}));
```

三个必须点（对应 01 文档 §6）：`base` / router base 一致；PWA `navigateFallback` 用完整子路径；
`404.html` 兜底。

### 2.2 Extension（MV3 多入口）

```ts
// packages/extension/vite.config.ts —— 三个独立入口，输出到 dist/
build: {
  rollupOptions: {
    input: {
      popup:    resolve(__dirname, 'popup.html'),
      options:  resolve(__dirname, 'options.html'),
      background: resolve(__dirname, 'src/background/index.ts'),
    },
    output: { entryFileNames: '[name].js', chunkFileNames: 'chunks/[name]-[hash].js' },
  },
}
```
- 静态资源（`manifest.json`、`icons/`、HTML）通过 `publicDir` 直出到 `dist/`。
- **不引入 `@crxjs/vite-plugin`**：其 beta 版本对 MV3 的 HMR 支持不稳定，手写多入口更可控。
- 生产构建关闭 `eval`（CSP 要求）：Vite 默认 production 不产生 `eval`，无需额外配置，但需在 manifest 中声明严格 CSP。

## 3. CI/CD（GitHub Actions）

### 3.1 `deploy-web.yml`

```yaml
name: Deploy Web
on:
  push: { branches: [main], paths: ['packages/web/**', 'packages/core/**', '.github/workflows/deploy-web.yml'] }
  workflow_dispatch:
permissions: { contents: read, pages: write, id-token: write }
concurrency: { group: pages, cancel-in-progress: true }
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: pnpm/action-setup@v4
        with: { version: 9 }
      - uses: actions/setup-node@v4
        with: { node-version: 20, cache: pnpm }
      - run: pnpm install --frozen-lockfile
      - run: pnpm typecheck
      - run: pnpm test
      - run: pnpm build
      - uses: actions/configure-pages@v5
      - uses: actions/upload-pages-artifact@v3
        with: { path: packages/web/dist }
  deploy:
    needs: build
    runs-on: ubuntu-latest
    environment: { name: github-pages, url: '${{ steps.deployment.outputs.page_url }}' }
    steps:
      - id: deployment
        uses: actions/deploy-pages@v4
```

> 前置手动操作（一次性）：仓库 Settings → Pages → Source 选择 **GitHub Actions**。

### 3.2 `release-extension.yml`

```yaml
on:
  push: { tags: ['ext-v*'] }
jobs:
  release:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: pnpm/action-setup@v4
        with: { version: 9 }
      - uses: actions/setup-node@v4
        with: { node-version: 20, cache: pnpm }
      - run: pnpm install --frozen-lockfile
      - run: pnpm build:ext
      - run: cd packages/extension/dist && zip -r ../../../extension.zip .
      - uses: softprops/action-gh-release@v2
        with: { files: extension.zip }
```

### 3.3 数据仓库的守护（可选，低成本高价值）

在 `my-collector-data` 仓库加一个 Action，每天检查数据完整性：

```yaml
# my-collector-data/.github/workflows/validate.yml
on: { push: { branches: [main] }, schedule: [{ cron: '0 3 * * *' }] }
jobs:
  validate:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: node scripts/validate.mjs      # 校验所有 JSON 可解析 + item 必填字段 + tagIds 引用存在
```

价值：一旦应用出现 bug 提交了坏数据，你能在当天收到 GitHub 的通知，而不是等到打开应用时才发现。

## 4. 测试策略

### 4.1 分层

| 层 | 工具 | 覆盖内容 | 目标 |
| --- | --- | --- | --- |
| 单元测试 | Vitest | `merge.ts`（冲突矩阵 14 例）、`shard.ts`（分片路由）、`filter.ts`（搜索）、`url.ts`（归一化/协议白名单）、`models`（守卫校验）、`planAffectedFiles` | **核心算法必须有测试** |
| 集成测试 | Vitest + MSW | `github/contents`、`github/gitData`（模拟 200/304/401/404/409/422/429/5xx）、`sync/engine`（pull→merge→push 全流程） | 关键路径 |
| 组件测试 | Vitest + @vue/test-utils | ItemCard 渲染、TagPicker 创建/去重、ItemEditor 脏标记逻辑 | 覆盖交互陷阱 |
| 端到端手测 | 手工清单 | 04 文档 §8 的 S1–S15，加本文 §4.3 的验收清单 | 发布前必过 |

### 4.2 必须写的单测（优先级排序）

1. `merge.test.ts` — 04 文档 §5.2 的 14 行冲突矩阵，逐行一个用例。
2. `engine.test.ts` — 断网写入 → 恢复 → 单次 commit 推送；422 → 合并 → 重试成功。
3. `gitData.test.ts` — 断言请求序列与 payload 结构（blob → tree → commit → ref），
   尤其断言 `base_tree` 与 `parents` 都正确。
4. `filter.test.ts` — 中文关键词、多词 AND、标签名命中、墓碑排除、归档隔离。
5. `base64.test.ts` — 含中文/emoji 的内容编码解码往返一致（`btoa` 踩坑回归测试）。
6. `url.test.ts` — 追踪参数剥离、`javascript:` 拒绝、相对 favicon 补全。

## 5. 交付里程碑

| 里程碑 | 内容 | 关键产出 | 验收标准 | 预估 |
| --- | --- | --- | --- | --- |
| **M0 骨架与连接** | monorepo；Vue3 + Tailwind + Router + Pinia；`core` 的 model/github client；设置页；连接测试；数据仓库初始化 | 能连上仓库、能初始化 4 个文件、能读出 meta | 首次引导走通；错误分支文案正确 | 1 单元 |
| **M1 核心闭环** | Dexie 本地库；`repository` CRUD；列表/新建/详情/编辑；标签创建与筛选；pull/push（无冲突处理） | 单设备完整可用：记录 → commit 上 GitHub → 换台设备能拉到 | 在 GitHub 上能看到条目 JSON 变化 | 1.5 单元 |
| **M2 同步健壮性** | outbox 队列；重试退避；合并算法 + 冲突矩阵单测；同步状态 UI；多标签页锁；限流处理 | 04 文档 S1–S15 全部通过 | 断网/并发/限流三类场景无数据丢失 | 1.5 单元 |
| **M3 检索与整理** | 关键词搜索；标签管理页（重命名/合并/删除）；批量操作；键盘快捷键；归档 | 检索与整理效率达到 PRD 预期 | 2000 条数据下搜索 < 50ms | 1 单元 |
| **M4 PWA 与移动端** | manifest + SW + 离线；分享目标 `/share`；404 兜底；移动端布局与 TabBar；深色模式 | 手机安装到主屏，分享可用，离线可用 | §4.3 的 PWA 清单全过 | 1 单元 |
| **M5 多入口** | Bookmarklet 生成器；Chrome 扩展（popup/options/背景/右键/快捷键）；扩展打包 Release | 四个入口都能记录 | §4.3 的入口清单全过 | 1.5 单元 |
| **M6 打磨与迁移** | 导出/导入 JSON；浏览器书签 HTML 导入；墓碑清理；Token 到期提醒；GitHub Actions 部署上线 | 可长期使用与备份 | 从 Chrome 导出的书签能批量导入并打标签 | 1 单元 |

> "单元"为相对工作量单位（1 单元 ≈ 一个专注工作日的产出），仅用于排序，不作为交付承诺。
> 每个里程碑结束都应产出**可运行、可验证**的版本，而不是半成品堆积。

### 5.1 建议的推进顺序理由

1. **M0/M1 先跑通"记录 → commit → 另一端能看到"**（AI方案 §10 的建议）——这是全案风险最高的假设，
   必须在早期被验证：GitHub Contents/Git Data API 的鉴权、CORS、base64 编码、sha 更新。
2. **M2 再补健壮性**——个人工具最容易死在"网络抖动导致数据不一致"，合并算法必须在有真实数据前就写好并单测。
3. **M4/M5 做入口**——入口是"体验加分项"，不是"能不能用"的前提条件。
4. **M6 做迁移**——先把日常用起来，再迁存量数据。

## 6. 风险登记册

| # | 风险 | 概率 | 影响 | 应对 |
| --- | --- | --- | --- | --- |
| R1 | GitHub Pages 子路径导致 PWA/路由失效 | 高 | 中 | 01 文档 §6 的四处一致性检查；发布验收清单专列一项 |
| R2 | 多端并发导致数据互相覆盖 | 中 | **高** | 04 文档的 CAS + LWW 合并 + 冲突矩阵单测；mergePolicy 可切换 |
| R3 | 中文内容 base64 编解码出错 | 中 | 高 | 统一 `TextEncoder/TextDecoder` 工具函数；专项回归测试 |
| R4 | PAT 泄露（扩展被投毒/依赖被投毒/误贴到公共仓库） | 低 | **高** | 权限最小化（仅 1 仓库 Contents RW）+ 90 天过期 + 严格 CSP + 依赖锁定 + Dependabot |
| R5 | 误删/误改数据 | 中 | 中 | 软删除墓碑 + Git 历史可回滚 + 设置页"导出全部 JSON" + 冲突时禁止强推 |
| R6 | 公共抓取代理不稳定或下架（r.jina.ai 限流/变更） | 中 | 低 | 双代理链 + 失败降级手动 + 可切自建 Worker + 结果本地缓存 24h |
| R7 | GitHub 限流 | 低 | 低 | 条件请求 + 跳过未变更文件 + 写去抖 + 精确 backoff 倒计时 |
| R8 | 数据仓库误设为 Public | 低 | **高** | 初始化时在 UI 明确提示"若为 Public，你的收藏将对所有人可见"；08 文档 §2.4 列入前置检查清单 |
| R9 | iOS 不支持 PWA 分享目标 | 高 | 低 | 帮助页给出 iOS 快捷指令方案 + 直接粘贴兜底 |
| R10 | 条目量增长后前端变慢 | 低 | 中 | 分片 + 虚拟滚动 + `filter` 纯函数优化；必要时引 Fuse.js/索引（02 文档 §5 触发条件） |
| R11 | 浏览器清缓存丢 outbox（未同步数据） | 低 | **高** | 有 pending 时顶栏常驻醒目提示；写入后 2s 内必尝试推送；提供导出备份 |
| R12 | Service Worker 缓存旧版本导致"改了没生效" | 中 | 低 | `registerType: 'prompt'` + 显式刷新提示 + `skipWaiting` 仅在用户确认后调用 |
